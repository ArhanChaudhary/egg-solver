Audit of inline measured-gain comments (main 52ab88f)

Historical snapshot. Its source, timings and pending statements belong to the recorded experiment, not the current checkout. Documentation home.

This audit checked that every notable optimization in the source carries an inline comment with its measured gain. Its result is one comment-only commit on 52ab88f, 68047f2 (9 files, +51/-34 lines; numbered 53fdbf1 while the audit was written), merged as 1f5eb70.

Source of every number: the commit and merge messages of git log main (first-parent merges and every merge's second-parent commits) and git notes; neg/* ignored. No number is new: each one below is quoted or computed from a before/after pair in the named commit. Basis labels: 48T / 1T = bench stream (20 30 48 L / 10 60 1 L), batch = the early bench.sh 1000-cube wall clock, thr = steady-state throughput of the early benches, nodes = nodes/cube (random:1000:2026 unless named), -c 1 / -c 0 = solve latency / random_state batch at 48T (ms/cube), bench share = bench random:1000:2026 ... share (solves/s).

Status: ok = an inline comment with the right number and basis was already there; added = new comment (or a number added to a comment that had none); fixed = number, basis or wording corrected; skipped = not annotated, with the reason.

Counts: see the end.

Numbers not found, and caveats

  • No change in main lacks a number where one was measured. The ones without an A/B say "not measured separately" (first-version techniques, c7's bookkeeping, the DFS write ring).
  • c7's tree sum and its ChildOrder write-without-read only have profile shares (2% and 2-3% of the samples), and the comments say so: they are not speedups.
  • m1's four, m3's three, skip-sibling's three, m7's five pieces and l6's pieces were measured only as stacks, and the comments say "part of".
  • Two existing figures are not literally in the commit messages, but they follow from them or come from the original experiment data, so they were kept: share.rs TRACE_* "+35%" (the counters' step, CUBE_TRACE=1 -> 3, is +29..36% in 3bf5530's table), and the LEAD_FRACTION replay's "20%" row (c11's replay output; the commit lists 10/30/50/70%).
  • m4's per-patch gains have no thread count in their source (per-patch A/B runs); the comments give them as "part of m4-micro's +7.7% at 48T", as before.
