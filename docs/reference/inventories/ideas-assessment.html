#IdeaStatus in our solverAction
1.1–1.5Faster table generation (scanning, batched writes, symmetry at the root)Affects only generation time. Our limit is RAM, not generation time.Use in the new any-k gen for laptop tables (p10).

2.2–2.4, 2.6Denser or entropy-coded tables (trits 1.25x, bitmaps, tANS ~1.5x, lossy)They only pay if the freed memory buys a bigger effective table, and H48 tops out at h11 (full EO).x-h48: feasibility study of a "bigger effective table within ~65 GiB": a coset refinement × an encoding, with the expected nodes gain and decode cost.
2.7Non-power-of-two sizes without divisionN/A: exact index, no hashing.none
3.1–3.4One big table; mean h is the key metric; nodes × size ≈ constantKnown; it guides the study above.—

3.8Table checksum before/after runsWe have table-meta validation, tabcheck and a read-only mapping.Optional --verify-table (xxhash) for the final comparison (p10).

4.8Symmetric inputs: search the first levels slowly, drop symmetric duplicates (symmetry² speedup)x-h48 is implementing symmetric start.Use Rokicki's deeper version; we report one solution, so the all-solutions caveat doesn't apply.
