cube48opt10: pruning-table file layout vs our h10

Method: static and read-only. I ran nm -C --defined-only, readelf -S -s, strings -n 6 and objdump -s -j .rodata on ~/cube48opt10, and objdump -d only on load_pruning_table, save_pruning_table, myalloc, set_prun, set_prun_min4, set_prun_hash and the call and constant lines of init_pruning_hash_table, fill_hash_table, fill_hash_table_iter and main. The binary was never run. Tags: [C] read directly from code or constants, [I] inferred.

Answer

Yes, the layout is the same. cube48opt10's file is the raw h10 table, with no header or trailer. It uses the same index layout, the same 2-bit code meaning, the same 16-byte groups with a 4-bit minimum in slots 0-1, and the same base, 10. Our /data2/tables/h10 is that same data region plus our 4 KiB trailer.

One known harmless byte difference. It affects the group-minimum nibble of groups whose entries are all greater than the base. cube48opt leaves those nibbles at 15, while ours stores 11 or 12. About 64% of groups in our file are like this. The solver never reads those nibbles, so a raw cmp will report differences there. Use the filtered compare in the last section.

Expected benign differences

  • Group nibble when every entry in the group is above the base. In cube48opt10, every table write in the hash path goes through set_prun_hash, which writes the nibble only when depth <= 10 [C]. So its nibbles are in {0..10, 15}. Our generator lowers minima through BFS level 12, so ours are in {0..12, 15}.
    • A 6 MiB sample of our h10, taken at 6 offsets, gave these nibble counts: 6:7, 7:149, 8:1634, 9:15915, 10:123158, 11:233397, 12:18956 [C].
    • The nibble is only read when the probed code is 0, which implies that some entry in the group is ≤ base. So nibbles above the base are never read [C, step1_query semantics; our collapse.rs also counts them as "unread_group_minima (harmless)"].
  • Slot 511 of each row, which no E placement maps to. cube48opt never writes it, so it stays at code 3 from the memset [C]. Ours is also 3: all 49,152 sampled rows had top bits 11 in byte 127 [C].
  • Not verified statically: whether the corner-class numbering, the representative/ttrep choice, the msplit rank, the EO bit order and the eslot order all match exactly. Our coord.rs says it follows cube48opt's layout. The compare below will settle it. [I]

Comparison recipe

Run cube48opt10 in an empty dedicated directory (call it DIR). It needs about 31 GB of free disk there, and a stale file in that directory would be loaded instead of generated. Then:

# 1. size: must be exactly the data size (no header/trailer)
stat -c %s DIR/h48prun31h1.dat                     # expect 31130910720

# 2. raw byte compare of the data region only; skips our trailer bytes [31130910720, 31130914816)
cmp -n 31130910720 /data2/tables/h10 DIR/h48prun31h1.dat
#    expect: a difference at some offset ≡ 0 (mod 16), from the benign nibble difference above

# 3. filtered compare: tolerate only (offset%16==0, same high nibble, ours>10, theirs==15)
nice -n 19 ionice -c3 cmp -l -n 31130910720 /data2/tables/h10 DIR/h48prun31h1.dat \
 | gawk '{o=$1-1; a=strtonum("0"$2); b=strtonum("0"$3);
          if (o%16==0 && and(a,240)==and(b,240) && and(a,15)>10 && and(b,15)==15) {benign++; next}
          real++; if (real<=20) printf "off %d ours %02x theirs %02x\n", o, a, b}
          END {printf "benign nibble diffs %d, real diffs %d\n", benign, real}'
  • cmp -l prints a 1-based decimal offset followed by the two bytes in octal. strtonum("0"x) parses the octal.
  • Expect roughly 1.2e9 lines of output. It is a streaming job: it reads 62 GB and is CPU-bound in gawk.
  • real diffs 0 means the tables are identical except for unread nibbles.

Alternative, semantic compare [I for the invocation; the logic is C from gen/collapse.rs and bin/gen.rs]:

  1. Write a sidecar with echo "10 10" > DIR/h48prun31h1.dat.meta (format: k base).
  2. Run ~/cube-opt/target/release/gen compare /data2/tables/h10 DIR/h48prun31h1.dat.

It prints same or DIFFERENT. It compares all 120,389,068,800 real entry codes and the group minima that are ≤ base. It uses thread_count() threads, so cap them on the shared machine.
