The Rust Performance Book: audit for cube-opt (pb1)

Historical snapshot. Its source, timings and pending statements belong to the recorded experiment, not the current checkout. Documentation home.

Source: https://nnethercote.github.io/perf-book/ (all 18 chapters, read in full from the book's print.html on 2026-11-04). Code refs are on main 7608a28 (x86 code identical to 3a9a50a); the deliverables are rebased onto 585b3b6 and the final PGO numbers were measured there. "Status" is one of done (with the commit or code), tried-negative (with the branch), N/A (with the reason), not yet tried, or newly tried (pb1) with the result. "Expected gain" is for the solver's measured workloads: bench stream (1T/48T), bench share, solve -c 1/-c 0.

Context that decides most rows: 1T stream spends 93% of cpu-clock samples in one function (bench::stream_thread, the lane loop), 2.4% setup_run, 1.6% next_run, 1.3% start_iteration, 1.2% extend_jobs, 0.21% kernel, 0.03% libc (malloc/free/memset/memmove together) (/data/agents/perfprof/stream1t.data, main 95cbb11). At 48T the limit is DRAM latency and memory-level parallelism, so instruction-count savings show mostly at 1T.

perf stat -e page-faults on a 1T stream run (5+30 s): 24.8K faults in total, nearly all start-up (24 lanes' buffers, cocsep generation). Had each of the ~940 sorts in such a run (1,889 allocations of >= 128 KiB, two per sort) faulted its two ~344-KB buffers in afresh, that alone would be ~160K faults. So glibc keeps them in its arena, and an alternative allocator or a reused sort buffer has nothing measurable to win.
