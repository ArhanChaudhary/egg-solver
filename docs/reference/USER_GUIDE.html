Build

cargo build --release --locked

The default x86 release targets the build machine's CPU. Build on the machine that will run the program, or choose a portable target. The library can be built without the CLI dependencies using --no-default-features.

Choose and generate a table

See table sizes. Choose a table that fits available RAM with room for the process and operating system. Generation and solve speed depend on CPU, memory and storage; server measurements are not laptop performance predictions.

mkdir -p tables
target/release/gen 7 auto tables/h7
target/release/gen check tables/h7

auto chooses the program's recommended compression base. The base changes pruning bounds, not data capacity. Generate once and reuse the file. The --parts N option generates row ranges sequentially to reduce peak memory in depth-first generation; it does not apply to h11's BFS generation. Memory and disk preflight checks run before generation; on hugetlbfs the disk check counts free huge pages, and --force skips the checks.

Solve scrambles

# One cube, using all selected threads:
target/release/solve --fast --table tables/h7 "R U R' U' F2"
# The same scramble from stdin:
printf '%s\n' "R U R' U' F2" | target/release/solve --fast --table tables/h7
# Batch: one scramble per input line:
target/release/solve --table tables/h7 < testdata/random_state.txt
# Complete one cube before starting the next:
target/release/solve --table tables/h7 -c 1 < testdata/random_state.txt

A cube can also be given as its 54 stickers instead of a scramble, wherever a scramble is read (solve, bench scramble files, --warmup): faces in the order U R F D L B, each read row by row as seen from outside (U with B at the top, D with F at the top, the side faces with U at the top), in any six symbols. This is what the web page shows for a random cube. A line of 54 symbols of six kinds without move suffixes is always read as stickers, also when the symbols are the face letters; if they are not the stickers of a cube that can be solved, it is an input error and nothing is solved. So a scramble of 54 moves of all six faces with no suffix at all must have one move written with the suffix 1 (U1 is U).

--fast requires an explicit --table. It does not search directories for tables. With no scramble arguments it reads exactly one nonblank stdin line. Empty input is an error, not a request for a random cube. An explicitly supplied empty scramble argument represents the solved cube. Warm-up is optional: --warmup SCRAMBLE adds one solve before the measured solve.

Batch mode also accepts a positional table path. EGG_SOLVER_TABLE can supply it in batch mode, and EGG_SOLVER_THREADS can supply the thread count. --fast still requires a command-line --table. Each EGG_SOLVER_* setting also accepts the matching CUBEOPT_* name from the project's earlier name as a fallback; an explicitly set EGG_SOLVER_* name takes precedence.

Search timing excludes table loading. The batch total measures completion of the whole batch; individual cube durations can overlap. See timing definitions before interpreting them as throughput.

Quarter-turn metric

By default every face turn counts as one move: the half-turn metric (HTM). With --metric qtm, solve and bench count quarter turns instead (QTM): a half turn such as U2 is two moves, and the solution is optimal in that metric.

# QTM with an HTM table (valid bounds, weaker):
target/release/solve --fast --table tables/h7 --metric qtm "R U R' U' F2"
# A QTM table gives tighter bounds for QTM solves:
target/release/gen 7 auto tables/h7q --metric qtm
target/release/solve --table tables/h7q --metric qtm < testdata/random_state.txt
Quarter-turn metric
Table--metric htm (default)--metric qtm
HTM table (gen K BASE OUT)YesYes: an HTM distance is at most the QTM distance
QTM table (gen K BASE OUT --metric qtm)RefusedYes

A QTM table is generated with the same tools and has the same size as the HTM table of its k. auto picks a base two above the HTM one for the same k (h0: 9, h7: 11), from the QTM depth distributions; it was not tuned by solve speed. Its trailer records the metric as the layout h48-qtm, so a build without QTM support refuses the table instead of treating its values as HTM bounds. A metadata sidecar for a QTM table reads k base qtm. gen check, gen derive and gen compare keep and compare the metric.

In QTM, each solved line reports the QTM length and ends with it, for example (22q), and the summary line ends with metric qtm; --fast prints the length as 22q. JSON output reports length in the search's metric and adds a metric field ("htm" or "qtm") in both metrics. The search keeps the 18 face turns in canonical order, charges a half turn two moves, and tries only lengths of the parity of the cube's corner permutation. A solution is printed in canonical form: two equal quarter turns where the two search directions meet become one half turn of the same QTM length.

God's number is 20 in HTM and 26 in QTM: the superflip needs 24 quarter turns, and the superflip composed with the four-spot pattern needs 26.

Measured on the 48-core server (2026-11-16, h7 tables copied into RAM with transparent huge pages, solve -c 1 -t 48, the first 50 states of testdata/random_state.txt): QTM on a QTM h7 (base 11) took 29.1 ms per cube on average (median 18.5 ms, 79 M nodes per cube), against 19.6 ms (median 11.0 ms) for HTM on the HTM h7. QTM on the HTM h7 took 549 ms per cube on the first 10 states, 19 times as long as with the QTM table. The states were 18 to 22 quarter turns from solved (21 for 27 of them). With the QTM h7, the superflip took 0.87 s (24 quarter turns) and the superflip composed with the four-spot 56 s (26). These are single runs on a machine shared with other work, not benchmarks.

All solutions

By default solve prints one optimal solution per cube. The shortest algorithm is not always the easiest to execute, so solve can also list every distinct solution up to a length:

# Every optimal solution:
target/release/solve --fast --table tables/h7 --all-optimal "R U R' U' F2 D L2 B"
# Every solution of at most one move more than optimal:
target/release/solve --fast --table tables/h7 --plus 1 "R U R' U' F2 D L2 B"
# Every solution of at most 12 moves, for each scramble of a file:
target/release/solve --table tables/h7 --max-length 12 < scrambles.txt
All solutions
OptionLists
--all-optimalEvery optimal solution; the same as --plus 0
--plus KEvery solution of at most K moves more than an optimal one
--max-length NEvery solution of at most N moves. With --plus K, the smaller of the two limits
--max-solutions MAt most M solutions per cube; the default is 100000
--time-limit SECONDSStop a cube's search after that time and list what was found; see stopping a list

The options work in batch mode and with --fast, with -t, -c, --json and --metric qtm. Without them the output is what it was before.

What a distinct solution is

  • Two sequences that differ only in the order of adjacent moves of opposite faces are one solution, since such moves commute: U D and D U. It is listed once, with U before D, R before L and F before B.
  • No two moves of one face follow each other, also after reordering commuting moves: U D U' is the one move D, not a solution of three moves.
  • A sequence with a part that does nothing is left out: it is a shorter solution with a loop added. A sequence that solves the cube before its end is one example. Such a part is a contiguous run of moves equal to the identity, in any order of its commuting moves. The shortest have 8 moves (U2 D2 R2 L2 U2 D2 R2 L2), so this only matters from 8 moves above optimal.
  • Everything else within the limit is listed, non-optimal solutions included. Among solutions of one length there is no ranking: they are sorted by length, then by their moves.

The solved cube has one solution, the empty one. Symmetric variants of a solution are different solutions and are all listed: the superflip has 4,416 optimal solutions of 20 moves.

Output

In batch mode each cube gets a solutions line, then one solution line per solution, shortest first:

solutions <index> <count> <optimal> <max> <nodes> <seconds>
solution <index> <length> <solution>
total <cubes> cubes wall <s> wall/cube <s> nodes/cube <n> threads <t> lanes <l> concurrency <c>

<max> is the length limit that was searched: the optimal length plus K, or N. <optimal> is - when the cube has no solution of at most <max> moves, which can only happen with --max-length. <seconds> runs from the cube's start to the end of its search. Every listed solution is replayed; a wrong one is reported as BAD <index> and makes the exit status 1.

With --fast the solutions are grouped under one line per length:

optimal  6 moves
listed   18 solutions of at most 8 moves (verified)
6 moves: 6 solutions
  U2 D2 R2 L2 F2 B2
  ...
8 moves: 12 solutions
  U D' R2 L2 F2 B2 U D'
  ...
time     1.636 ms   (0.2 M nodes, 100 M nodes/s)

With --json, each cube is one object; --fast --json prints the same fields with table, threads, lanes, scramble, ms and nodes_per_second, without type, index and ok:

{"type":"solutions","index":0,"count":2,"optimal":4,"max_length":4,"truncated":false,"stopped":null,"complete_length":4,"metric":"htm","by_length":[{"length":4,"count":2}],"solutions":[{"moves":"U2 D2 R2 L2","length":4},{"moves":"R2 L2 U2 D2","length":4}],"nodes":1380,"lookups":192,"seconds":0.000451741,"ok":true}

The limit on the number of solutions

The number of solutions grows about 13 times per extra move, so a list is capped at --max-solutions solutions. A cube with more is never cut silently: its search stops, and the output says so.

The limit on the number of solutions
OutputA truncated list
Batch textA line truncated <index> <M> <complete> after the cube's solutions line
--fast textA line truncated: there are more than M (--max-solutions); complete up to L moves
JSON"truncated":true and "complete_length":L

A truncated list holds M solutions: all those of at most <complete> moves, and some of the next length. Raise --max-solutions or lower the length limit to get a complete list.

Stopping a list

A list can take very long: every further move multiplies the search by about 13, and --max-solutions bounds the list, not the time. Two things end a list early and still print what was found:

  • --time-limit SECONDS stops each cube's search that many seconds after its start. Fractions are accepted (0.5). It is not an error: the exit status stays 0.
  • Ctrl-C (SIGINT) stops the lists being searched. The cubes of a batch that were not started are left out, the total line counts the cubes printed, and the exit status is 130. A second Ctrl-C ends the program at once. Without the list options Ctrl-C ends solve as before.

A stopped list is marked like a truncated one, with the reason and the largest length up to which it is complete:

Stopping a list
OutputA stopped list
Batch textA line stopped <index> time <complete> or stopped <index> cancelled <complete> after the cube's solutions line
--fast textA line stopped: the time limit was reached; complete up to L moves or stopped: cancelled; complete up to L moves
JSON"stopped":"time" or "stopped":"cancelled" (otherwise null) and "complete_length":L

It holds every solution of at most <complete> moves and whatever was found of the longer ones. If no solution was found yet, the count is 0, <optimal> is - (null in JSON; with --fast, optimal more than L moves), and <max> is the limit as far as it is known. The search looks at the clock when a job of the cube ends and at the Ctrl-C flag once per round of its lanes, so it stops within milliseconds, not inside its inner loop.

$ solve --fast --table tables/h0 -t 4 --max-length 15 --time-limit 0.3 "R U F2 D L' B"
optimal  6 moves
listed   7145 solutions of at most 15 moves (verified)
stopped: the time limit was reached; complete up to 14 moves
6 moves: 1 solution
...

Limits and cost

Searches go up to 20 moves, God's number, and to 26 quarter turns with --metric qtm; --max-length above that is refused, and --plus K stops there. In QTM the lengths are QTM lengths, all solutions of a cube have the same parity, and a half turn is written as one move (U2, never U U).

A list costs more than one solution, because the search cannot stop at the first solution: it must finish the optimal length, and then each further length takes about 13 times the nodes of the one before. The table shows the 25 scrambles of each optimal length from the nissy benchmark sets on h7: nodes per cube, and the solutions of all 25 cubes together.

Times per cube, measured on the 48-core server with nothing else running (2026-11-20, h7 copied into RAM with transparent huge pages, 48 threads, -c 1, one run per cell): the 17-move scrambles took 3.8 ms for one solution, 12 ms for all optimal ones and 113 ms with --plus 1; the 18-move scrambles 21 ms, 107 ms and 1.41 s. The 16-move row was timed only with 16 threads while other work ran on the machine, so it is indicative: 1.5 ms, 5 ms, 33 ms and 0.37 s with --plus 2.

All threads work on one cube, as for a single solution (-c 1, --fast), or on the cubes of a batch. A search for a list does not use the solution-first job order, which only serves to find one solution sooner; pruning by table bounds is unchanged.

Symmetric cubes

A cube with symmetries (a rotation or reflection that leaves it as it is) has its solutions in groups: the image of a solution under such a symmetry is another solution. A list then searches only one job of each group of first moves that the cube's symmetries map onto each other, and adds the images of every solution it finds. The list is the same as without this, and the search is shorter by up to the number of symmetries, 48 at most. Only the cube's own symmetries are used for this. A symmetry that takes the cube to its inverse is not, and neither are first moves that happen to reach equivalent positions: the single-solution search skips those too, but their solutions are different sequences that no symmetry gives back.

The superflip, which has all 48 symmetries, has 4,416 optimal solutions of 20 moves. Listing them on h7 with 48 threads took 6.7 G nodes and 3.1 s; without this reduction (the build before it) the same list took 260 G nodes and 98 s (48-core server with nothing else running, 2026-11-23, -c 1; two runs and one run). nissy-core, with the limit of its solution count removed, lists the same 4,416.

The lists were checked against brute force on short scrambles and on symmetric positions with 2 to 48 symmetries (tests/all_solutions.rs), and against nissy-core's lists on these sets (solve_file h48h7 FILE 999999 K, each solution put in the same order of commuting moves). Both programs list the same solutions: the 27, 36 and 140 optimal ones of the 16-, 17- and 18-move sets, the 67 and 278 up to one move above optimal of the 16- and 17-move sets, and the 453 up to two above of the 16-move set.

Tune and benchmark

target/release/bench tables/h7 tune
target/release/bench --help

The tune command measures how fast solve searches (nodes per second on random states, for about three minutes) with 8 to 48 lanes per thread, in its two modes (a batch, and one cube at a time on all threads) at 1 thread, half the threads and all threads, and writes the best lane count of each to a <TABLE>.tune record (the default of 24, unless another count is more than 1% faster: the measurement is no finer than that). solve takes the entry of its mode at the nearest thread count (nearest as a ratio: 4 threads use the entry of 8, not of 1). The best lane count depends on the CPU, mostly on its caches and on whether two threads share a core, so tune on the machine that solves, with nothing else running. A table on hugetlbfs (any mount, not only /mnt/huge) cannot hold small files, so its record goes to tables/<NAME>.hugemeta.tune in the build checkout, beside the optional tables/<NAME>.hugemeta metadata sidecar; rebuild on each machine so that path is local, and keep table names distinct across hugetlbfs mounts. solve and bench use a matching record unless -l is explicit. The built-in lane candidates end at 48, but explicit larger lane values are supported. The measured lane study has lane screens of one machine.

Records of the earlier tune command (those without the first line # egg-solver tune 2) are not used, and solve -v says so. That command counted the cubes that a stream of random states finished in six seconds, which on tables up to h9 is a handful at one thread, so its choice was close to chance; and it measured bench stream's search, not the one solve runs. Run the tune command again to replace such a record.

The historical positional benchmark syntax remains supported. Use bench --help and each subcommand's help for named syntax, warm-up and measurement windows. Record the actual command with benchmark output.

Table files

A table has pruning data and a 4 KiB metadata trailer containing k, base, distribution and checksum (and, for a QTM table, the metric). Padding can separate data and trailer. gen check TABLE verifies stored integrity; a checksum alone does not prove that every bound is admissible.

Table files
Load modeStorage used during searchNotes
--load copyPrivate RAM populated before searchingDoes not keep reading the original file for lookups; still requires enough physical RAM
--load mapRead-only file mappingResident hugetlbfs data is RAM-backed; an ordinary file mapping can fault pages from disk
--load shm / --shmLinux System V shared-memory segmentReuse an existing segment or create one from the file
--load autoExisting matching shared segment; otherwise the platform defaultOn Linux: map RAM-backed files, copy ordinary files; otherwise follow the platform default

EGG_SOLVER_LOAD sets the mode. Mapping and shared-memory storage must remain unchanged while the solver uses it. Prefaulting touches mapped/shared pages at startup; --prefault 0 defers that work until first use. Prefaulting is not a guarantee that an ordinary mapping can never be paged out.

The 1 GiB-page benchmark policy describes those recorded experiments. It is not a requirement to reserve huge pages for the small quick-start example.

Table files and shared-memory segments created before the project was renamed remain usable; the pruning data does not need to be regenerated.

Shared memory on Linux

target/release/solve --shm-load tables/h7
target/release/solve --shm --table tables/h7 < testdata/random_state.txt
target/release/solve --shm-remove tables/h7

A segment persists until removal or reboot. An existing matching segment avoids reloading the table into a fresh private allocation. Metadata is checked on attachment; a mismatched segment is rejected by explicit shared mode. Keep the segment and table immutable during use.

A segment holds the table file's bytes, with the file's trailer (k, base, size, distribution and checksum) in its last 4 KiB. The trailer is written last, after the copied data's checksum is checked, so a segment without one is still loading or was interrupted. --load auto passes over a segment that does not match the table file and loads the file instead. A loaded segment is read-only: ipcs -m shows perms 400 (600 while loading).

The segment key is the ASCII bytes "co" (0x636f, a legacy prefix kept for compatibility), then the table's k and base, one byte each: ipcs -m shows h7 base 9 as 0x636f0709 and h11 base 10 as 0x636f0b0a. A QTM table's key has the top bit of the k byte set (0x636f870b for QTM h7 base 11), so tables of both metrics can be loaded at once. --shm-key (or EGG_SOLVER_SHM_KEY) selects another key, for example for two tables with the same k and base.

--shm-pages 1g requests only 1 GiB pages and fails if unavailable. The default page preference is 1g,2m,4k; -v reports the selected size and fallback reasons. Huge-page allocation needs both permission (the configured huge-page group or CAP_IPC_LOCK) and enough free reserved pages. The program's preflight reports relevant limits: kernel.shmmax, kernel.shmall and kernel.shmmni, then the huge-page permission and free pool pages, or free memory for 4 KiB pages. Attaching an existing segment needs no free memory.

On a typical Linux host, the one-time root setup for huge-page segments looks like this; adapt it to the host and the loader's diagnostic:

# Permission: a group of yours as the huge-page shared-memory group
sudo sysctl vm.hugetlb_shm_group=$(id -g)
# Free pages: reserve N 1 GiB pages (or use hugepages-2048kB for 2 MiB pages)
echo N | sudo tee /sys/kernel/mm/hugepages/hugepages-1048576kB/nr_hugepages

A file in /etc/sysctl.d keeps the group setting after reboot. 1 GiB pages are most reliably reserved at boot with the kernel parameters hugepagesz=1G hugepages=N.

ipcs -m lists segments. Removal releases memory after the last process detaches. These system settings depend on the host; read the loader's diagnostic before changing them.

Portable builds

On x86, replace the native target flags to build for another CPU:

RUSTFLAGS="-C target-cpu=x86-64-v4" cargo build --release --locked
RUSTFLAGS="-C target-cpu=x86-64-v3" cargo build --release --locked
RUSTFLAGS="-C target-cpu=x86-64" cargo build --release --locked
cargo build --release --locked --target aarch64-apple-darwin

The targets above require AVX-512-class features, AVX2/BMI2-class features, baseline x86-64, or Apple Silicon respectively. Cross-compilation also needs the target toolchain and linker. The portable fallback is available through the library's scalar feature for correctness/backend checks.

WebAssembly

rustup target add wasm32-wasip1 wasm32-wasip1-threads
wasm/build.sh

This creates wasm/dist/egg-solver.wasm and egg-solver-threads.wasm. The wrapper supplies the required WASI interface for browsers and Bun:

import { EggSolver } from './wasm/egg-solver.mjs';
const solver = await EggSolver.create({ wasm: 'wasm/dist/egg-solver.wasm' });
await solver.loadTable('h6');
// Or generate a small table with the recommended base:
// await solver.generateTable(4);
solver.solve("R U R' U' F2");

solve puts the selected workers on one cube and returns { moves, length, metric, nodes, lookups, seconds }; solveMany uses independent cube lanes. solveAll(cube, { plus, maxLength, maxSolutions, timeLimit, metric }) lists every distinct solution up to a length (by default the optimal ones) and returns { solutions: [{ moves, length }], count, optimal, max_length, truncated, stopped, complete_length, by_length, metric, nodes, lookups, seconds }. timeLimit (seconds) stops the list with stopped: 'time'. With the threads build another thread can stop a running solveAll: solver.cancelHandle is { buffer, offset } (the module's shared memory and its cancel word; null for the single-thread build), which can be posted to another thread, and the exported cancel(handle) there makes solveAll return what it found with stopped: 'cancelled'. Both take { metric: 'qtm' } for the quarter-turn metric (by default the table's metric: HTM for HTM tables), and generateTable(k, base, { metric: 'qtm' }) makes a QTM table; length is in the solve's metric. loadTable accepts a path (Bun), a URL, a File or Blob, or the file's bytes. Inputs can be scrambles or 54-sticker facelet strings in U R F D L B face order, each face viewed from outside and read row by row (U with B at the top, D with F at the top, the side faces with U at the top); any six symbols can stand for the colors. The wrapper's facelet parser checks the representation.

Bun

bun wasm/demo.mjs --table tables/h6 < testdata/random_state.txt
bun wasm/demo.mjs --gen 4:8 --random 5:1
bun wasm/demo.mjs --table tables/h6 --threads 8 --batch < scrambles.txt

The second command generates h4 with base 8 in memory and solves five random states.

Browser

bun wasm/serve.mjs

Open the local URL printed by the server, or the public site, https://egg-solver.arhan.sh/. The page has one job. Type a scramble, or paint your cube's colours on an unfolded net (pick one of the six colours, then click or drag over stickers; the centres are fixed, white on top and green in front), and press Solve: the net gives way to a 3D cube that plays the shortest solution, one animated face turn at a time. A slider and the moves themselves jump to any point of the solution, a play button replays it, dragging turns the cube around, and Edit cube returns to the net. Random scramble fills in 25 random turns. A cube given as its 54 stickers can be pasted into the field too.

On load the page starts with every core the browser reports and prepares its table, with no choice to make: h4 with base 8 (464 MiB) on desktops, h3 (232 MiB) on phones, tablets and devices reporting 4 GB of memory or less; if one cannot be prepared it falls back to a smaller table, down to h2 and h0. A prepared table is exported as a table file (EggSolver.exportTable) and kept in the browser's IndexedDB, so later visits load it, checksum checked, in about a second instead of generating it again; tables that earlier versions of the page kept (other kinds, quarter-turn tables) are deleted. With the WebAssembly build in Bun at 14 threads on the EPYC VM, 12 random states (all 18 moves) took a median of 3.5 s each with h4 base 8, 2.1 s with h4 base 9, 4.9 s with h3 and 7.8 s with h2; base 9 took about 90 s to build against 9 s for base 8, which is why the page uses base 8. The h4 study records the base tradeoff. Most cubes take seconds; the few that need 19 or 20 moves can take minutes. While a solve runs the button reads Stop, which ends the solver's worker and starts a new one that reloads the saved table.

Every solution is checked on the page's own sticker model (wasm/cube-model.mjs), which also explains why a painted cube cannot be solved (a wrong count of a colour, an impossible piece, a twisted corner, a flipped edge or two swapped pieces) and outlines the stickers concerned. The 3D picture (wasm/cube-3d.mjs) is drawn in SVG without a library; wasm/test.mjs checks that the way it turns a layer agrees with the sticker model for all 18 moves.

Two selectors under the field say what to search for. The first is how moves are counted: the half-turn metric, or the quarter-turn metric, which has a table of its own (h4 with base 10, or h3 or h2 on smaller devices), prepared and kept separately. The second is which solutions to find: one shortest solution, all shortest solutions, or all of up to 1 or 2 moves more than the shortest. In quarter turns it offers up to 2 quarter turns more instead: all solutions of a cube are odd or all are even there, so 1 more would list nothing new. A list holds up to 2000 solutions, says how many there are of each length, and any of them can be chosen and replayed. Stop ends a list and keeps what it found, with the length up to which it is complete (through the module's cancel word, cancel(solver.cancelHandle); without threads nothing can reach a running list, so it ends by itself after a minute).

The page leaves out the rest of what the module can do: several cubes at once, a chosen thread count, other table sizes and loading a table file. Those are in the module's API (above) and in the command-line programs. In Bun with 8 threads on an 8-core Apple M2 (2026-11-16, single runs, nothing else running), QTM tables h3, h4 and h5 of base 10 took 85–91 s each to generate, against 14 s for HTM h4 base 8; QTM h4 base 11 was still generating after 7 minutes. On six random states they took 3.1–54 s (h3), 1.7–17 s (h4) and 0.6–15 s (h5) per state, against 1.9–6.9 s for HTM solves on HTM h4 base 8; a QTM solve on that HTM table took 47 s on the state the QTM h4 solved in 1.7 s.

Tables

The wasm32 build supports h0–h6. Each Rust allocation must fit below isize::MAX (2 GiB), so h7 is rejected even though wasm32 has a larger overall address space. The table and the module's other allocations must also fit the host's memory limits. Large tables are normally generated with native gen and then loaded.

Threads

Browser threads need SharedArrayBuffer and cross-origin isolation. The local server supplies the required COOP/COEP headers, and the public site, egg-solver.arhan.sh, receives them from Cloudflare because GitHub Pages cannot set headers. The solver runs in a Web Worker because its thread waits cannot run on a browser's main thread. On a host that cannot send the headers, such as a plain github.io deployment, the page registers wasm/coi-sw.js, a service worker that adds them, and reloads once; where a browser refuses it, the page uses one thread. Bun supports the threaded wrapper without those HTTP headers.

The wrapper initializes the module and worker pool. Other hosts must call the module's _initialize once before any other export, then egg_solver_after_initialize if the module exports it (modules built with Rust 1.100 or later, whose wasi-libc supplies _initialize). See wasm/src/lib.rs and the JavaScript wrapper when embedding it directly.

Tests

scripts/check.sh runs the library tests in WebAssembly under wasmtime and wasm/test.mjs (both modules in Bun) when those tools are installed. The wasmtime runner needs wasi-threads support (wasmtime 44 or older; set WASMTIME=path to choose a binary). Missing tools are reported, not counted as passing.

Performance records

Historical V8/Bun timings, generation times and engine warm-up experiments are kept under Historical measurements. They are not predictions for a current browser or laptop. Performance studies indexes the measured native and WebAssembly evidence.

Library use

Cube::from_bytes, symmetry-coordinate lookups and cube_from_edge_key return Option for invalid input. Table and solver internals are exposed through read-only accessors. H48Table::from_memory checks the metadata and allocation size; get returns None for an invalid index.

H48Table::open_copy loads the table into private RAM and is safe. APIs that map files or attach shared segments are unsafe: the backing storage must remain unchanged and untruncated while the table exists, including changes by other processes. The command-line mapped and shared modes require the same condition; --load copy avoids that dependence after loading. File-backed generation requires exclusive access to its output paths. Safety describes the undefined-behavior evidence and its scope.

The packed-coordinate and table encodings require a little-endian target; big-endian builds are rejected at compile time.

Every distinct solution of a cube up to a length comes from Solver::all_solutions (one thread, the reference search) or lanes::share::all_solutions (all threads on one cube, or a batch), with the limits in solutions::Options and the list in solutions::Solutions.

The WebAssembly build was about 5.7 times slower than the native x86 build in this record, with the same solutions and node counts. NEON was only run under qemu, which says nothing about speed. Two things mattered for WebAssembly speed:

  • WebAssembly has no prefetch instruction: prefetch::read_once is a plain load there, which starts the cache miss just as well (+53% in wasmtime, +45% in V8). Lanes still paid off: 1 lane 200.6 s, 8 lanes 123.8 s, flat up to 64; the module used 16.
  • V8 (Chrome) starts new code in its baseline compiler and gives a function optimized code only from its next call: a long first solve would run slowly to its end (187.7 s instead of 129.5 s). loadTable and generateTable therefore run a short warm-up (warmUp, then ~0.6 s), and all exports share one copy of the search loop. JavaScriptCore (Bun, Safari) moves a running loop to optimized code: in Bun the warm-up is skipped (126.5 and 127.2 s without it, 127.0 and 127.9 s with it).

With 8 threads (egg-solver-threads.wasm, one L3 domain), one cube at a time got 7.2-7.8 times the one-thread speed (h6: 88.6 Mnodes/s in V8, 90.7 in Bun; in headless Chromium 0.63-0.66 s instead of 5.15 s for the same cube), and generating h4 base 8 took 13 s instead of 75 s.

Node counts matched the native ones (h5, 20 random states: identical nodes, lookups and lengths natively, in wasmtime and in V8; h6, 100 depth-17 cubes: the same in Bun). Sources: db0b8ac and cc43b77.
