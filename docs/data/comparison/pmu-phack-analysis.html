Scope and measurement quality

This is the dual-socket Xeon X5650, family 6/model 44, with 12 physical cores and 24 logical CPUs. The tested source is 935cb7fa369248161244507b7c13aa9c405f9ff1, plus the included profiling-control patch, compiled for Westmere. The table is h6, 1,945,686,016 bytes (1.946 GB / 1.812 GiB). This is a separate host/build/table dataset from the EPYC comparison matrix. It predates the rename and the current Miri-driven safety fixes; those fixes cannot be credited as measured here.

Each run loads the table, warms for eight seconds, then enables counting through acknowledged perf control FIFOs for approximately 20 seconds. Observed controlled windows are 20.0001–20.0037 seconds. Table load/generation are excluded. Hardware events count user execution. IPC and event/instruction ratios use counters from the same run and event group. Different auxiliary events were measured in separate windows, usually once; critical events have three repeats. Ratios across different events are estimates, not simultaneous observations.

Two optional text exports failed: instruction annotations selected the wrong hot symbol, and sample listings requested a CPU field absent from five profiles. The raw profiles contain samples. All six annotations and sample listings were recovered locally using the returned symfs; outputs and replay checks are in phack-analysis/reporting-replay/. Focused cycle annotations of the actual run_lanes symbol are also in phack-analysis/cycles-{one,physical}.annotate.txt. No host rerun was needed. The collector's “valid” status describes measurement, not successful generation of every optional postprocessing file.

Cycle profile and counter evidence

The search loop accounts for 97.34% of one-thread cycle samples and 97.36% at 12 physical workers. Ordinary cycle sampling can skid, so an individual annotated instruction's percentage is not its exclusive cost. Both recovered annotations concentrate on the same hot regions, with integer/vector unpacking, stack traffic and loop control visible. This locates work; it does not prove an optimization or its gain.

Intel defines these model-specific events in its Westmere catalogue. The stall events must not be added into a pie chart or interpreted as a complete partition of execution time. These are older PMU events, not a modern Top-Down analysis. The very large difference between generic request misses and retired-load misses means the latter cannot stand for all memory traffic. This dataset alone does not distinguish speculative requests, prefetch timing and other event-definition or hardware effects behind that difference.

Dividing separately measured normalized outstanding-read occupancy by busy cycles gives roughly 1.1 outstanding reads while busy. This is an approximate demand-read concurrency metric; it excludes other traffic and is not total system MLP or DRAM bandwidth. The interleaved 12-worker run shows remote DRAM responses near half of the two captured local/remote response classes, consistent with placement. No memory-controller bandwidth measurement was collected, so bandwidth saturation is not established.

Inference: the strongest optimization leads on this Westmere build are the search loop's instruction delivery and scheduling/dependency pressure, with page translation also material. The measurements do not justify treating DRAM bandwidth as the sole bottleneck or predicting gains on the EPYC build.

The separate thread sweep observed 1.60 solves/s at 12 workers and 1.20 at 24 workers. The baseline observed 1.55 and 1.40 respectively. SMT increases counted instruction execution modestly but does not improve completed-solve throughput in these windows. Aggregate SMT IPC uses the sum of both logical threads' cycles; it cannot be read as physical-core IPC.

Use 12 physical workers as the candidate for a longer matched validation, not as a proven universal setting. One-socket scaling also varies: counted cycles per worker per wall second are lower at 6 workers than at 1 or 12. The archive does not include per-window CPU temperature/frequency telemetry or enough controls to identify the cause. Do not attribute this confidently to NUMA, throttling or software contention.

The 4 KiB intervention really disabled THP for the table. Median IPC changed from 1.762 to 1.610 at 1 worker and from 1.767 to 1.617 at 12 workers. That is an instruction-execution signal in favor of THP for this workload, but not a measured percentage improvement in completed solves: one-thread solves/s remained quantized at 0.15, and 12-worker completion rates overlap.

CPU 1 belongs to node 1 on this host. The local test put the table on node 1; the remote test put it on node 0. The latter also had only 89–91% THP coverage versus 99.92% locally, so it changes two conditions. Both completed 0.15 solves/s and IPC was 1.760 local versus 1.743 remote. This cannot establish a clean NUMA latency penalty. The 12-worker baseline table was split approximately equally between the nodes, as requested. No 1 GiB hugetlb measurements exist in this archive: the optional intervention was skipped because suitable existing pages were unavailable. No kernel huge-page pool was changed.

Linux documents AnonHugePages as the amount of anonymous memory backed by THP in its THP guide. These are placement snapshots, not continuous residency measurements.

Eight and 12 lanes show the highest observed completion counts, but there are only 0–5 completions per window. Zero completions does not mean zero work: those runs have billions of counted instructions and unfinished searches. Lane count also changes the instruction mix. Neither IPC nor Ginst/s can replace an exact completed-work denominator here. Warm-up and end-of-window in-flight work can change which cubes finish. Do not claim a 67% speedup or change the default lane count from this sweep. A longer, interleaved, same-cube validation is required before adopting a performance change.

The share=1 runs use cooperative latency semantics and are not a directly equivalent throughput comparison with independent stream workers. Their counters are retained in the raw dataset; no cross-mode speedup is claimed.

Precise sampling and useful next experiments

All DWARF cycle, LBR, branch PEBS and load PEBS captures succeeded. The two load profiles are sparse: 55 retired-LLC-miss samples and 41 latency samples above 128 cycles. The latter have observed weights 129–534 cycles, median 193. This is a threshold- selected tail with only 41 samples, not the mean or distribution of all loads. The 55-sample LLC profile is dominated by setup paths and cannot establish their share of total cache-miss cost accurately.

The existing data supports investigating hot-loop instruction footprint, unpacking and register/stack pressure first, while retaining THP. It supports testing 8/12 lanes and 12 physical workers with longer, matched solves. Changes still need correctness/Miri checks and measured 1T and full-machine gains before adoption. No performance code was changed on the strength of this archive. A complete repeat of all 242 runs is unnecessary to recover annotations or to retain these counter findings; any follow-up should target the unresolved throughput ranking and, if needed, a NUMA test with matched page coverage.
