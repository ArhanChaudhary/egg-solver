Assessment — 2026-11-07 15:18:23 UTC

The evidence supports the conclusion that the identified UB mechanisms have been addressed in the validated code, which was integrated into main as a247321. This assessment does not claim that every possible execution is free of UB. Both complete Miri catalogues passed, as did the source-bound native/backend, focused Miri, ThreadSanitizer and AddressSanitizer checks. The relevant implementations are table ownership and getters, search publication, staged-sort publication, and the shared-memory payload reader. The additional audit record distinguishes reproduced failures from manual findings and defensive hardening.

Mapped storage deserves a precise qualification. Marking an API unsafe documents who must uphold its storage contract; it does not prevent a different process from modifying or truncating the backing file. The CLI's mapped/shared modes still require that contract. H48Table::open_copy instead creates private RAM, removing dependence on subsequent external changes to the file. The assessment is conditional on the contracts of whichever storage mode is used.

What the completed evidence establishes

The complete x86 Miri run finished at 08:52:15 UTC on the candidate's exact source fingerprint. Its catalogue contains 56 named tests: 50 executed successfully and six explicitly ignored. All names were accounted for. Four shared-search tests ran under each of 16 scheduler seeds, giving 64 shared-search test executions; these repetitions do not increase the number of distinct test names. The previously unfinished checksum test passed. The first complete x86 acceptance record lists the source fingerprint, compiler, flags, test names and exclusions, and the raw run log records completion.

The portable Miri run also completed successfully: 54 catalogued names, 48 executed unique tests and 6 explicitly ignored tests. All 16 shared-search seed harnesses passed all four tests. The checksum and lane-splitting groups finished. See the portable acceptance record for the exact source and validation timestamp.

The final portable lane-splitting test was still active as its original four-hour wrapper limit approached. At 10:35 UTC, the existing watchdog was extended by setting three hours of remaining time, giving a deadline of 13:35 UTC. At 13:03 UTC, with the same test still active and no reported failure, a second bounded extension set three hours remaining, ending at 16:03 UTC. Neither operation restarted or attached a debugger to the interpreter, or changed its source, test inputs or checks; only the timeout supervisor's timer changed. These deadlines are bounds, not ETAs or passing results. Evidence: first extension, second extension.

Native/backend validation, focused strict-provenance Miri, ThreadSanitizer and AddressSanitizer all passed on the same candidate fingerprint. These methods add different evidence: Miri checks executed Rust-level accesses and aliasing; the sanitizers exercise instrumented native executions; backend and correctness tests check behavior on their selected inputs. Agreement between them is useful, but their coverage overlaps and none independently proves the complete program sound. In particular, AddressSanitizer does not verify Rust's full aliasing rules, and ThreadSanitizer does not explore every possible schedule.

The earlier candidate passed native checks, focused Miri and ThreadSanitizer before the tracing regression exposed another defect. That is a concrete reason to remain cautious, not merely a theoretical disclaimer: the earlier passing tests did not exercise the relevant overlap. The new tracing test improves that coverage, but cannot establish that no similar untested transition exists. Earlier validation and tracing finding.

What still prevents a stronger conclusion

Exclusions and scaleThe six ignored x86 Miri tests remain exclusions. The interpreted searches use smaller fixtures and fewer workers than production, and Cargo integration tests are outside this Miri runner. Keep native evidence separate and preserve these limits in any final claim.
Source and configuration changesRecheck applicable invariants and rerun relevant validation after edits, compiler changes or newly supported targets. A passing source fingerprint does not certify later source bytes.

The project's no-panic requirement is a separate property from memory safety. Replacing a checked access with an unchecked access is justified only by a sound invariant. The no-panic scanner passing is evidence about the constructs it scans, not proof that every possible implicit panic has been eliminated. Likewise, solution replay and optimality comparisons address solver correctness; they do not establish absence of UB.

For candidate 13307ba, the supported conclusion is: the identified failure mechanisms have fixes supported by code review and completed regression checks, with no further UB reported in those completed executions. Both complete Miri runs and integration are finished; absence of UB across all supported executions remains unproven.

Defects Miri actually exposed

  1. The safe memory-view API permitted an invalid aliasing sequence. A program using only safe calls could keep a shared byte slice, obtain atomic words for the same allocation, write through them, and then read the old byte slice. Miri reported that the write invalidated the byte reference's borrow tag.

    The reproduction was:

    use egg_solver::tables::Memory;
use std::sync::atomic::Ordering;

fn main() {
    let memory = Memory::anonymous(8).unwrap();
    let bytes = memory.bytes().unwrap();
    let words = memory.words().unwrap();
    words[0].store(1, Ordering::Relaxed);
    std::hint::black_box(bytes[0]);
}

    This is a diagnostic test program; its unwrap calls are not proposed production code. The candidate makes the atomic-word accessor and low-level generator entry unsafe with explicit caller obligations, and updates internal callers. The old safe reproduction is now rejected with compiler error E0133. The positive test tables::tests::atomic_updates_finish_before_byte_reads passed under Miri. Requiring an unsafe block prevents this particular misuse through an entirely safe call sequence; it does not prove every unsafe caller meets its contract.

    Evidence: original Miri diagnostic, compile-fail rejection, positive-test log.

  2. A dependency's futex syscall arguments had an incompatible C-variadic type. A scheduling-seed run reached parking_lot_core 0.9.12's Linux futex wait. Miri expected a raw *mut u32 argument and received an atomic reference. It reported undefined behavior at that call. The candidate vendors the dependency and applies explicit raw-pointer argument conversions, including the timeout pointer's type. The subsequent 16 shared-search seed harnesses completed without that diagnostic.

    Evidence: original futex diagnostic, candidate dependency implementation, subsequent seed logs.

These are positive demonstrations that the testing found defects. They are also reasons not to describe main at this snapshot as established to be UB-free. The preserved evidence does not establish that ordinary solver use triggers every defect; the first reproduction establishes a safe-public-API soundness problem.

Complementary evidence and its limits

Native tests, backend builds, clippy, search-identity checks and hot-instruction comparisons have passed for the safety candidate. They provide regression and compilation evidence, not a proof of memory safety. Mordant completed on the inspected snapshots and highlighted, among other things, the unsafe Sync implementation around CubeCtx's UnsafeCell<Inner>. Its correctness depends on the shared-search ownership and publication protocol and requires manual review. Native evidence, Mordant report.

The project's ban on intentional runtime panic calls is a separate property. Avoiding a panic does not make an unchecked pointer/index valid. Safe failure handling, successful solves, and zero explicit panic macros do not establish absence of UB.

Outstanding work at this snapshot

  1. Complete the exact-source x86 and portable Miri attempts, retain failures and exclusions, and integrate the safety fixes only after their validation gates pass.
  2. Audit every unsafe operation's bounds, initialization, alignment, lifetime, aliasing, provenance and synchronization preconditions, including whether safe public callers can violate them.
  3. Audit the CubeCtx publication/reclamation protocol and dependency FFI boundaries. Use targeted tests and concurrency modeling where they can test a concrete invariant; 16 scheduling seeds are not a substitute for that analysis.
  4. Review actual native assembly/SIMD and OS-backed memory paths using appropriate native checks. Miri fallback results alone cannot close those gaps.
  5. Tie subsequent evidence to the final merged source and its compiler/configuration. Any changed source needs its own applicable validation.

At this snapshot, no formal verification of the complete codebase has been performed. The supported claim is that Miri detected specific defects and found no further UB in the completed executions of the corrected candidate. Absence of UB throughout the codebase remains unestablished.
