Original experiment record

wasm: threads build hang fixed (wasi-libc init, threads that never exit, memory that never grows); wasm steps of check.sh time-limited

node wasm/test.mjs hung intermittently inside check.sh (main 8977134). The main thread sat in a futex wait and the workers were idle. Under load there were three faults in the threads build, which the fixes below remove.

  1. No wasi-libc init. A Rust cdylib gets no _initialize (wasi-libc's crt1-reactor), so __wasi_init_tp never ran and the main thread's pthread record stayed zeroed. Threads were linked into wasi-libc's thread list through that record, and the list came apart: an exiting thread could find itself alone in it and call exit(0) (musl's last-thread path) instead of waking its joiner, so join waited forever. Traced runs (spawn/start/end hooks, 8 at a time on CPUs 0-7): 219 threads ended in proc_exit(0) over 23 traces, and 6 of 9 runs hung, as in m8's check.sh. Fix: an _initialize export (__wasi_init_tp, then the linker's ctors, as crt1-reactor does), which cubeopt.mjs already calls on the main thread before anything else.
  2. One thread per share and call. A worker becomes free only after its thread has returned to it, a moment after Rust saw the thread finish, so a solve right after another could find no idle worker (EAGAIN, an abort: 5 of 13 runs under load). A spawn cannot wait for one either: the spawning thread holds wasi-libc's thread-list lock, which an exiting thread needs (traced: 4 exits went through together the moment a waiting spawn gave up after 60 s). Fix: threads that never exit. parallel::set_runner lets a host run on_threads on threads of its own (unset natively: the same scoped threads as before). The threads build installs wasm/src/threads.rs, a pool started as needed and never ended. The module's share-mode solve now goes through on_threads (Pool::new plus pool.run on every share: share::solve_all without its scope).
  3. Shared memory growing while threads run. In V8, a bulk memory operation checks its bounds against the size its instance last saw, which a grow updates only later. A memory.fill of a block fresh from malloc trapped with "memory access out of bounds" (named build: in share::Bufs::sized, right after malloc). This hit 3 of 176 test.mjs runs and 1 of 100 t.mjs runs; with the heap grown once in _initialize, 0 of 100. Fix: the threads build imports all of wasm32's memory from the start (--initial-memory, 4 GiB less one page, so that __heap_end fits in 32 bits), so it never grows. wasi-libc's malloc has the whole heap, and tables::Memory uses posix_memalign there instead of memory.grow (C's allocator is not limited to isize::MAX, so h7 still fits). The engine maps the 4 GiB, and untouched pages cost no RAM.

Also:

  • A thread that traps now writes its error at once and, in Node, ends the process, instead of hanging silently. (A Node worker's console goes through the main thread, which may be the one waiting.)
  • check.sh: the wasm library tests run under timeout -s KILL 600 per test binary (in the cargo runner), and wasm/test.mjs under timeout -s KILL 300. A hang fails the check at once, with a message.
  • README: other hosts must call _initialize first.

  • t.mjs (threads module: h0 with 3 threads, then 20 rounds of 6 share-mode solves and a batch, ~140 parallel jobs per run): 100 runs, all ok.
  • The threads demo path, beside t.mjs (demo.mjs --table h4 --threads 4, 10 depth-15 cubes one at a time, then --batch): 40 runs, all ok.

  • check.sh passes, including the wasm library tests under wasmtime and test.mjs. One earlier run hit the known scalar Worker::release flake (r8).
