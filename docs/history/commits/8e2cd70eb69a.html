NEG (no code): in-house items kept after inspection (d1 crate sweep)

Items of the crates.io sweep that were not swapped, with the reason. Each would add a dependency without removing work (the user's rule: a crate only where it is at least as fast, measured):

  • arrayvec / smallvec for the explicit stacks (Lane::stack: [Node; MAXD] with a depth index; Piece::nodes) and the buffers (Lane::jobs, Bufs): the stacks are fixed arrays indexed by depth (unchecked since m8), an ArrayVec adds a length and capacity checks on push; every Vec is allocated once and reused (Bufs::touched, Pool::spare), so a SmallVec saves no allocation on any warm path.
  • crossbeam-deque / crossbeam-channel / rayon for the share mode's work distribution: there is no hand-rolled deque. Jobs are claimed in chunks from one claim word (count << 32 | next) by a fetch_add, which a deque cannot beat for a fixed, sorted array; pieces go to idle threads through one-slot mailboxes (IDLE/WANT/FILL/FULL CAS states, no allocation): a channel allocates or locks per message (l6-share-2 measured a Mutex<Option> slot at bench share 827 vs 845/s). The staged build sort is a cooperative sample sort run by the pool's own waiting threads; rayon's fork-join cannot be driven from the pool's protocol.
  • rayon for parallel::on_threads (generation, table loads): a thin wrapper over std::thread::scope (or, since 3a9a50a, the wasm runner hook); the loops inside claim chunks from an atomic counter (dynamic balance already), with a handful of coarse tasks per pass. A global pool and work stealing add nothing, and on wasm rayon would need its own pool setup next to p11's runner.
  • parking_lot for the cold mutexes (tables.rs SPARE_PAGES at table load, parallel.rs runner results, the bins' stdout/record mutexes, once per solved cube): never contended on a timed path; no performance reason. (The share mode's warm mutexes did switch: see the parking_lot commit.)
  • xxhash-rust (xxh3) for the table checksum (tables/file.rs chunk_hashes: 4 multiply-rotate lanes per 32 bytes, in parallel): a different hash changes the checksums in every existing table trailer (/mnt/huge and /data tables, stamped by p10), and the check is memory-bound anyway.
  • rand / fastrand for cubie::Rng (SplitMix64): it generates the benchmark and verify sets (random:N:SEED); another generator changes every set and the verify.sh reference numbers, and it is not on a timed path.
  • std OnceLock statics, std::thread::scope: already std.
