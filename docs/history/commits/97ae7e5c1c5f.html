lanes: read the next lane's lookup ahead, and the prune bound

NEGATIVE (not for merge). Against cb8cb70 (= fc6d9c9's tree).

Idea: the prune branches of a visit (po > r1, pm > r1, and the exhausted-node test after the face cut) wait for the pending value: lane state load -> table word load -> shift -> code. A diagnostic that adds 9 cycles to that chain (3 dependent imuls on the value) costs 1.7% more than the same imuls off the chain (1T, 3 runs: main 21.533, on-chain 20.950, off-chain 21.317), so the chain's latency counts.

This version (the last of four):

  • each visit loads the next lane's table word (Solver::value_word, the load half of value) into that lane's k_word. The visit then needs only k_word & 3 and the base (the code-0 path loads the group minimum as before). A spare lane past the active ones absorbs the read-ahead of a round's last visit;
  • the pending child's r - 1 is kept in the lane (k_remaining), so the prune tests do not wait for sp -> node loads.

Search unchanged. But every version is slower:

  • the read-ahead takes one visit of slack from each lookup, at a lane count that is already short of slack (16/20/28 lanes: -9.6% / 0 / +10.2% at 1T);
  • the extra loads and stores raise register pressure: the TABS base register is lost, so each table access needs an lea.
