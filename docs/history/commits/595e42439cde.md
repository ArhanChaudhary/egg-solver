## Original experiment record

bench: each mode's thread code compiled on its own

`bench`'s thread closure ran either the share mode (`Pool::run`) or
the stream loop (`run_lanes`), and LLVM inlined both into it, so the
stream loop's register allocation and stack frame depended on
share.rs. For example, the stream code of bench at main differs from
that of c7 without l6-share-2, although lanes.rs is the same.

Each mode now runs in a function of its own that is not inlined:
`share_thread` and `stream_thread`. `stream_thread` is byte-identical
(addresses aside) whether it is built on main or on c7 without
l6-share-2, so changes to share.rs no longer change the stream code.
Its placement in the binary still moves with any change, as every
function's does. solve has no stream mode, and its binary is
byte-identical to main's. examples/xsolve.rs still runs both modes from
one closure.

A first version also made `Pool::run` #[inline(never)]. That moved
solve's `rounds` from 16 to 48 mod 64, and solve -c 0 at 1 thread lost
1.5% (a layout effect: with all functions aligned to 64 bytes, the
difference was 0.2%). The share mode is left as it was.

solve is byte-identical to main's. bench share's search is unchanged
(the same nodes and lengths), and verify.sh gives main's numbers
(nodes/cube 3089312 lookups/cube 2616086; 3990866 / 3378144). The c7
reference here is 21e3ca9 with f2cb1f4 cherry-picked, built in the same
folder. Without f2cb1f4, the binaries' layout depended on the build
folder, and c7 vs main measured -1.1..-1.4% then.
