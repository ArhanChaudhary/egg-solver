## Original experiment record

Job handling: radix sort, shared inverse lookups, pipelined extension, job prefetch

A perf profile put job handling at ~6% of samples: the stable sort_by of
~43K jobs (2.9%, comparator recomputes job_weight with a mispredicting
branch), start_iteration/extend_jobs (1.9%), and the jobs[job_pos] load
in setup_job (1.4%; 16 lanes interleave ~516 KB job streams, so it misses).

- Sort: stable LSD radix sort of (inverted f32 key bits, index) pairs,
  then a gather. Keys are non-negative floats, so the order matches
  total_cmp exactly, ties included (new unit test
  sort_jobs_matches_stable_sort). job_weight is branchless.
- extend_jobs: only X children get an inverse lookup; X2 inherits the
  parent's li and X' copies its X sibling's (same coset identities as the
  search). 1.33 instead of 2 index computations + lookups per job.
  Lookups pipelined with 48 in flight; cubes computed once per parent.
- A jobs_tmp buffer is kept per lane (~1 MB job memory per lane).
- setup_job prefetches the job 8 entries ahead.

Search is unchanged (depth18: 3607979 nodes/cube, lengths 18:100;
random:1000:2026 identical nodes/lookups per the m2 subagent).
