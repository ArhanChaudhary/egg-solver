diag: prune outcome of each lookup by the node's bound on that side

DIAGNOSTIC (not for merge). Against cb8cb70 (= fc6d9c9's tree).

Counts every resolved lookup by its kind (other side of X; moved side of X, X2, X') and by r - bound of the node on the looked-up side (lo for the other side; a new Node::lm for the moved side). It also counts whether the child was pruned (value > r - 1). bench prints the table after a batch.

random:200:2026 (7 threads, 20 lanes), counts (pass / prune):

lookupr-bound 0123+
other (X)43.7M / 294.0M17.6M / 35.1M4.76M / 5.91M1.30M / 1.83M
moved X6.94M / 23.5M17.1M / 12.0M6.03M / 0.24M1.45M / 0.09M
moved X24.27M / 13.8M15.2M / 10.1M5.71M / 0.18M1.46M / 0.06M
moved X'6.92M / 18.0M16.9M / 11.8M5.87M / 0.18M1.39M / 0.07M

What follows:

  • The other side's bound says little about whether the X child's lookup prunes. Even at r - lo = 2 it prunes 55%: the table is far from consistent below its base, where code 0 falls back to the group minimum and the corner depth. So issuing an X child's moved-side lookup together with the other side's when the other side looks loose wastes over half of them (cf. neg/m4-pair-lookups).
  • The moved side is predictable by class (77% / 41% / 4% prune), but the class is high-entropy itself. Feeding it to the predictor (a per-class dispatch or an early branch) would add about as many early mispredicts as it removes late ones.
