wasm: SIMD128 backend; the library runs in WebAssembly (WASI, with and without threads)

User request: "towards the end, make it also compile to wasm". The crate now builds and runs for wasm32 with the same searches, tables and node counts as natively. The next commit adds the module for browsers and Node.

  • src/portable/v16_wasm.rs: V16 on SIMD128 (core::arch::wasm32):

    • lookups: u8x16_swizzle (indices from 16 give 0, as NEON tbl);
    • the byte shift left: an add;
    • the movemasks: bitmask of a 16-bit-lane shift (bit 7 of each byte still comes from its own byte). build.rs picks cfg(backend = "wasm") for wasm32 with simd128. .cargo/config.toml turns simd128 on for wasm32 targets, and sets the maximum memory of wasm32-wasip1-threads to 4 GiB (the linker's default there is 1 GiB). New test v16_matches_scalar (NEON and wasm): every operation against the scalar reference on 20,000 random vectors, lookup indices over 0..255.

  • Targets:

    • wasm32-wasip1: one thread.
    • wasm32-wasip1-threads: std threads through wasi-threads, so share mode and multi-thread stream mode run unchanged (stable Rust, no build-std).
    • wasm32-unknown-unknown: keeps compiling. Its std has no clock (Instant panics there).

  • prefetch::read_once is a one-byte load on wasm32, which has no prefetch instruction. The CPU runs on past a pending load, so the miss overlaps the next lanes' work just as with a prefetch. That makes it an unsafe fn (p must point into an allocation); the two callers pass table entries. On x86 and aarch64 the instructions are the same as before.   • src/parallel.rs: on_threads(n, f) runs share 0 on the calling thread and spawns n - 1 threads, so one thread spawns nothing (wasm without threads). It replaces the spawn loops of the generators (gen.rs, gen/dfs.rs, gen/collapse.rs), of distribution and of file::checksum. The work split is the same as before.

    • Regenerated h7 base 9 (8 threads) vs p10's /data/agents/p10/h7b9: gen compare finds 0 differences in codes and group minima, and the data is byte-identical (cmp). Only the trailers differ: p10's file predates the layout line.
    • gen check passes on /mnt/huge/h7, h8 and h11 (read-only).
    • Generation speed is unchanged. h4 base 9 on 8 threads of one L3 domain, alternating, main def2cd0 vs this commit:
      • main: 26.7 s and 26.6 s (depth-11 pass 20.1 s, 20.0 s);
      • this commit: 26.6 s and 26.4 s (19.9 s, 19.8 s);
      • outputs byte-identical.

  • Memory on wasm32: whole pages from memory.grow, not from the allocator, which cannot hand out more than isize::MAX = 2 GiB at once (h7 is 3.6 GiB). Linear memory never shrinks, so the next table reuses the pages of a dropped one. Memory::try_anonymous (non-unix) reports out-of-memory instead of aborting. On 32-bit, bytes and words assert the 2 GiB slice limit.

  • H48Table::from_file_memory(memory, verify, threads): a table file whose bytes are already in memory (copied there by JavaScript). It is checked like open: trailer, k, base and sizes, and with verify the checksum (over pieces of at most 1 GiB).

  • LoadMode::Auto is Copy where there are no mappings (WASI, Windows). map failed there.

  • bin/gen compiles on WASI: positioned writes by seek + write, no getrusage.

  • cubie: CubieCube::from_facelets and to_facelets, in Kociemba's 54-sticker order U R F D L B with any six color symbols. Tested on:

    • known strings (solved, U, R, superflip);
    • round trips and recolorings;
    • rejected non-positions.

  • Tests that assumed 64 bits or unix:

    • scratch files go through scratch_path (WASI has no temp dir and no process id);
    • the hot-index test uses a one-page stand-in table, since it only computes indices and a zeroed h11 cannot be allocated on wasm32;
    • the read-only-mapping test runs only on Linux.

  • check.sh:

    • clippy for wasm32-unknown-unknown (lib), and for wasm32-wasip1 and wasm32-wasip1-threads (all targets);
    • the wasm library tests under wasmtime, when installed (WASMTIME=path, else skipped with a note).
