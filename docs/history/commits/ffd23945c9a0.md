## Original experiment record

tables: shared memory segments (--shm), as vcube's (user request)

"do something similar to vcube and allow the user to use Shared memory".

`solve --shm-load TABLE` (vcube: `vc-optimal --no-input --shm`) copies a
table file into a System V shared memory segment that stays in memory
after the process exits, until reboot or `solve --shm-remove TABLE` /
`ipcrm`. Later runs attach it read-only: `--shm` (= `--load shm`,
`CUBEOPT_LOAD=shm`; solve, bench, cubeopt) attaches it or makes it first,
and the default `--load auto` attaches it when it is there. `--load map`
and `--load copy` never use a segment.

Design (src/tables/shm.rs):
- Key: ASCII "co" (0x636f), then k, then base: 0x636f0709 for h7 base 9,
  0x636f0b0a for h11 base 10 (`--shm-key` / CUBEOPT_SHM_KEY for another).
- Layout: the table file's bytes as on hugetlbfs: data at offset 0 (same
  alignment as a hugetlbfs map), the file's trailer (k, base, size,
  distribution, checksum) in the segment's last 4 KiB, plus
  `segment-page-bytes` and `segment-source` lines (keys Trailer::parse
  ignores). The trailer is written last (its first byte with Release),
  after the copy's checksum has been checked against the file's trailer;
  then the segment is made read-only (mode 0400) and attached SHM_RDONLY.
- Every attach compares the segment's trailer with the table file's: a
  segment of another table under the key is refused by --shm (with how to
  remove it) and passed over by auto (note, file loaded as before). A
  segment without a trailer is being loaded (maker alive: --shm waits,
  auto loads the file) or was interrupted (maker gone, nobody attached:
  --shm removes it and loads again). Tables need a trailer checksum.
- Pages: 1 GiB, then 2 MiB (SHM_HUGETLB | log2 << 26), then 4 KiB, as
  `--shm-pages` / CUBEOPT_SHM_PAGES allows. Preflight before each size:
  kernel.shmmax / shmall / shmmni; for huge pages the permission
  (vm.hugetlb_shm_group or CAP_IPC_LOCK, checked first, as the kernel
  does) and free pool pages (free - resv + overcommit - surplus). A huge
  size that cannot be had is skipped with a note saying how to get it
  (sysctl, nr_hugepages), EPERM/ENOMEM from shmget too. Free memory for a
  4 KiB segment is u1's cli::preflight::memory (as for a copy), from
  LoadArgs::preflight: tables::shm::new_segment_page says which page size
  a new segment would get, and tables::shm::loaded lets auto/--shm skip the
  copy preflight when the table's segment is there (an h11 segment on 1
  GiB pages needs no free memory). -v logs the page size; a 4 KiB segment
  (when huge pages were allowed) gets a warning on every run.
  CUBEOPT_SHM_DENY_HUGE (tests, undocumented) simulates the missing
  permission without asking the kernel.
- A failed load removes its segment (RemoveOnDrop); read_parallel now
  returns read errors instead of panicking (copy loads get the error too).
- The table's Memory is the attachment itself (munmap detaches as shmdt
  does: segments are whole pages, so the length is the mapping's): no new
  field in Memory or H48Table.
- Linux only (cfg(all(target_os = "linux", not(miri)))): elsewhere --shm
  fails with ShmUnsupported and auto skips segments.

H48Table::open_reporting returns a LoadReport (mode used, segment, notes);
open_with is unchanged for callers. LoadOptions gains shm_pages and
shm_key (gen's literal uses ..Default).
