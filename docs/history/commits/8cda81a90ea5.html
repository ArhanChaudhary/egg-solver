NEGATIVE m7: read-ahead (not merged)

From a3eb8bf5e3ddb7457425c21bd0a474dc00a0f6ad Mon Sep 17 00:00:00 2001 From: Ubuntu super@claude-cube.usubflgyqkfexnnpr2q2liw1rb.bx.internal.cloudapp.net Date: Tue, 3 Nov 2026 23:55:17 +0000 Subject: [PATCH] lanes: read the next lane's lookup ahead, and the prune bound

NEGATIVE (not for merge). Against f2cb1f4 (ported from cb8cb70; c7's per-root-child statistic kept).

Idea: the prune branches of a visit (po > r1, pm > r1, and the exhausted-node test after the face cut) wait for the pending value: lane state load -> table word load -> shift -> code. A diagnostic that adds 9 cycles to that chain (3 dependent imuls on the value) costs 3.1% more than the same imuls off the chain (1T at 24 lanes, same build folder, 3 runs: main 24.533, on-chain 23.300, off-chain 24.050), so the chain's latency counts.

This version (the last of four):

  • each visit loads the next lane's table word (Solver::value_word, the load half of value) into that lane's k_word. The visit then needs only k_word & 3 and the base (the code-0 path loads the group minimum as before). A spare lane past the active ones absorbs the read-ahead of a round's last visit;
  • the pending child's r - 1 is kept in the lane (k_remaining), so the prune tests do not wait for sp -> node loads.

Search unchanged. But every version is slower:

  • the read-ahead takes one visit of slack from each lookup, at a lane count that is already short of slack (16/20/28 lanes: -9.6% / 0 / +10.2% at 1T);
