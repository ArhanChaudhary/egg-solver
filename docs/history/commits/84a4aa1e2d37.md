## Original experiment record

backends: portable cube (NEON, scalar; wasm ground) next to the unchanged x86 one

User request: run on a laptop (Apple Silicon), later in wasm. The x86 code
needs AVX2 + BMI2 everywhere and AVX-512 in a few lanes helpers; now the
crate builds and runs on any target, with search results identical to the
bit on every backend (same coordinates, same tables, same node counts).

Selection at compile time (build.rs): cfg(backend = "x86") for x86_64
with AVX2 + BMI2, "neon" for aarch64, else "scalar" (also forced anywhere by
the `scalar` cargo feature, to test the portable code on this machine), and
cfg(avx512) for the x86 backend with AVX-512 F/BW/VL. No runtime dispatch.

- x86: simd.rs and the x86 bodies in coord.rs and lanes.rs are unchanged;
  coord.rs's BMI2/movemask functions get cfg attributes (three one-line
  cfg twins for a pext/pdep inside shared functions); lanes.rs's AVX-512
  helpers (quantize18, sum18, codes_above, max_code, the compress-store of
  build_first) get #[cfg(avx512)] and portable twins, bit-exact vs the
  originals over 2M random inputs (sum18 replays _mm512_reduce_add_ps's
  order of additions, so job statistics, and with them node counts, stay
  identical); _bzhi_u32 gets a portable twin; the _mm_prefetch sites
  (lanes, share, solver, tables, gen) call src/prefetch.rs (same
  instructions; prfm on aarch64, nothing on wasm).
- src/portable/: the cube as two 16-byte halves (`V16`): NEON (vqtbl1q_u8
  lookups, the three edge movemasks by bit weights + 4 vpaddq, vbsl
  select, umaxv tests) or plain arrays (the reference). Index bytes that
  carry orientation bits are masked to their piece before a lookup (tbl
  gives 0 from index 16, vpshufb ignores bits 4..6). Portable coord parts:
  the two constant-mask pexts of cocsep by multiplies (no carries: proof in
  the comment), the 12-bit pext by two 6-bit lookups, eo pext of a
  contiguous mask by a shift.
- m7's x86 helpers have portable twins: `Cube::select_mask` (the mask's
  low byte as the bsl/blend mask), `Cube::child_lookup` (one composition of
  selected operands, with the move cubes kept whole for it), the move_face/
  move_kind/move_keep/x_move_mask tables, and the `SymEdge` eo fold (Tinv's
  eo by source position xored before the position lookup); `hot_section!`
  and the hot functions' link_section apply only on x86-64 Linux (ELF
  syntax; Mach-O and wasm have neither), elsewhere they are no-ops.
- wasm ground: Memory without mmap (allocator) and table I/O without unix
  APIs off unix; `cargo clippy --target wasm32-unknown-unknown --lib`
  passes (no wasm build or run yet).
- .cargo/config.toml: target-cpu=native only for x86_64 targets (it named
  the x86 host CPU for cross targets; aarch64-apple-darwin defaults to
  apple-m1). Same flags as before for x86 builds.
- check.sh also clippies aarch64-apple-darwin, aarch64-unknown-linux-gnu,
  wasm32 (lib) and --features scalar, and runs the library tests with the
  scalar backend and, under qemu (when installed), with NEON; skipped with
  a note where a target or tool is missing, CHECK_BACKENDS=0 skips all.

Validation:
- NEON, aarch64-unknown-linux-gnu under qemu-user: the whole test suite
  passes (25 library + 14 integration tests: stream lanes, share mode, the
  recursive solver, conjugates in all modes, the table generators).
- scalar backend on x86 (--features scalar): the whole suite passes
  (integration correctness checks passed).
- test cross_check (x86 test builds): portable vs x86 cube operations and
  every coordinate along random move walks (so with the unspecified bytes
  as the operations leave them).
- Search identity (count.sh-style, 8 threads, deterministic): on h11
  random:1000:2026, main f8a4919, this x86 build and the scalar backend
  (--features scalar) all give nodes/cube 3058198, lookups/cube 2588380,
  lengths 15:1 16:35 17:270 18:662 19:32 ; NEON under qemu vs x86 on the direct h7 base 9,
  random:40:2026: both nodes/cube 40317075, lookups/cube 34322539, the
  same lengths. (The same held before the m7 rebase, vs 735dd25.)
- Other x86 builds: RUSTFLAGS="-C target-cpu=x86-64-v3" (the x86 backend
  without AVX-512: portable lanes helpers) passes the whole suite incl. the
  cross-check; "-C target-cpu=x86-64" (no AVX2: scalar picked
  automatically) passes it too.
- check.sh on this machine, all backends: 3 min 48 s (CHECK_BACKENDS=0
  skips the backends).
- x86 hot loops instruction-identical to main f8a4919 (objdump, addresses
  normalized): bench::stream_thread 1470 instructions, share Worker::rounds
  1225, Worker::restart 1460, lanes::run_lanes 320, Lane::advance 341,

- x86-64-v3 builds (cfg(avx512) off) contain no AVX-512 instruction (0
