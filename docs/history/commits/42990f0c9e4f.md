## Original experiment record

b2: read-ahead with eager sibling clearing (negative, -11.0%)

ra6: the read-ahead with bookkeeping and unified dispatch
(neg/b2-readahead-bookkeeping-dispatch, included here) plus eager
sibling-face clearing in the read-ahead: a face whose bound exceeds the
remaining depth is cleared from todo per face (per-face stores, to avoid
a store-forwarding failure) as soon as its value is read.

Why: drop pruned siblings without visiting them.

48 threads (bench /mnt/huge/h11 stream 20 30 48 16, solves/s, same run,
1 run each):

| build                                  | solves/s | change vs main |
|----------------------------------------|----------|----------------|
| main fe58740                           | 671.8    |                |
| read-ahead value only (ra2p)           | 641.9    | -4.4%          |
| + bookkeeping, unified dispatch (ra5p) | 617.7    | -8.0%          |
| + eager sibling clearing (ra6p)        | 597.6    | -11.0%         |

1-thread solves/s: not recorded.

Conclusion: each added piece made the read-ahead slower. Eager sibling
pruning itself was right: done at note time without the read-ahead
machinery it became the skip-sibling patch (7a173a1, +13.6%). Here it
likely just adds stores to the already heavier read-ahead path.
