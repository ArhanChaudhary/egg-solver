## Original experiment record

m4: diagnostic, extra index computation and prefetch per child (negative, -16.8%)

Diagnostic, not a candidate. In advance, every generated child also
computes the table index of its moved-side cube (s.index(a2)), prefetches
that line and stores the index (k_idx2) so it is not optimized away. For
an X child this is a second, distinct DRAM line; for X2 and X' it is the
line already being looked up.

Why: price the paired-lookup idea (neg/m4-pair-lookups): what an extra
index plus a real DRAM fetch per X child costs.

48 threads (bench /mnt/huge/h11 stream 20 30 48 20, capped, interleaved,
3 runs, solves/s):

| build                    | run 1 | run 2 | run 3 | median |
|--------------------------|-------|-------|-------|--------|
| main ff2b7a4             | 821.2 | 826.3 | 829.0 | 826.3  |
| + extra index + prefetch | 685.4 | 688.4 | 687.8 | 687.8  |

Change: -16.8% (median); per run -16.5, -16.7, -17.0%.
1-thread solves/s: not recorded.

Conclusion: an extra index plus a prefetch per node costs about 17%. The
index alone costs about 13% (neg/m4-diag-extra-index), so the extra DRAM
traffic adds about 4%. Paired lookups cannot win.

Source: scratchpad m4/neg-diag-extra-index-prefetch.patch (= diag-dbl),
made against ff2b7a4; applies cleanly.
