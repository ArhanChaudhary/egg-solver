## Original experiment record

lanes: order root children across jobs in the iterations on unchanged jobs (c7, v2)

In stream mode ~45% of a cube's nodes are in the last iteration, which
finds its solution after ~6% of its tree, and ~51% in the exhaustive one
before. Jobs (4-move prefixes) were run whole in the order of one
statistic each. This patch orders (job, root child) pairs across all jobs
in the iterations whose jobs are those of the previous iteration (the
jobs have their full length; with h11 T >= 18: the likely last ones,
every one but the last exhaustive, where order does not matter).

- Statistic per root child: the lookup terms (8^(16-h)) of a run are
  summed per root child in `Lane::cheur[stack[1].m]` (at the root, the
  pending child: `advance` writes its move to `stack[sp + 1].m` when it
  generates it, branch-free). At the end of a run of a full-length job the
  sums become 8-bit codes (4 steps per octave, +1 step for faces 1, 3, 5:
  12 instead of 15 continuations; -0.6% nodes) in `JobX::ck`, a 32-byte
  record per job beside `jobs`, with the root's X values (`tw`) and the
  children run in this iteration (`done`, tagged with the target).
- Full-length job roots branch on the normal side (ck refers to its
  moves). Costs +1.3% nodes in T=17 alone; better than keeping the free
  side choice and running inverse-side jobs whole (-5.1% instead of
  -5.7% combined over the two tuning sets in an earlier configuration).
- Split iteration: first part = the root children with the best codes,
  about FIRST = 20% of all of them (threshold from a sample of 1/8 of the
  jobs), counting-sorted by decreasing code across jobs; reaching an entry
  runs its child with the job's other not-yet-run candidates at most one
  octave lower (MERGE). Then the rest (built only if the first part is
  exhausted): one run per job with children left, by decreasing best
  remaining code. Every (job, child) runs exactly once; at T >= 18 no root
  pruning interacts across runs (child bounds <= 13 < r); an X' child run
  without its X sibling takes X's other-side value from `JobX::tw`
  (position-only), else X runs too.
- The job-end path is out of line and cold (`next_run`: record the run,
  set up the next, or the next iteration); the run state is boxed
  (`RunState`) to keep it off the lane's hot lines; a whole run's
  `JobX` entry is written without reading it (it is not cached; reading
  it cost 2-3% of samples) and prefetched for writing at setup; the sums
  use a tree reduction (a sequential f32 sum was 2% of samples).
- Share mode keeps its ordering (whole jobs by statistic); its job
  statistic is now the sum of `cheur` at `JobDone` (share.rs: two resets).

Tuned on random:1000:2026 and random:3000:777 (FIRST 0.03..0.3, MERGE
2..12 steps, face bias 0..2 steps, rest order, side handling); checked on
random:2000:31337. Unit test `split_runs_cover_each_child_once` drives
the run machinery with simulated outcomes over random jobs and checks
coverage, side and X' values; debug assertion at every split iteration's
end.

`tw` (written only when the X child passes), a value that pruned X in the
whole run before the first split iteration is not recorded: such an X'
then runs with its X (`JobX::tw` unknown).

On 78ce33e, per node the stream cost ~4% more than main (1T perf, stream window:
69.9M vs 73.1M nodes/s): job bookkeeping outside the loop 3.3% of
samples (next_run, setup_run, start_iteration) vs main's inlined
setup_job, and ~1% in the loop (the per-child slot; 0.5% for the
store-based slot vs 0.8% for a select on sp).
