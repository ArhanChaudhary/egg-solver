## Original experiment record

m4: diagnostic, 50% random branch resolving after the lookup (negative, -15.1%)

Diagnostic, not a candidate. As neg/m4-diag-brE-incl-c6, but the random
branch's condition also depends on the node's todo after the resolve, so
it resolves late (after the looked-up value is known).

Why: measure whether late-resolving mispredicts cost more than early
ones.

48 threads (bench /mnt/huge/h11 stream 20 30 48 20, capped, interleaved,
3 runs, solves/s):

| build                      | run 1 | run 2 | run 3 | median |
|----------------------------|-------|-------|-------|--------|
| c6 (previous commit)       | 877.6 | 879.6 | 884.0 | 879.6  |
| c6 + early random branch   | 768.8 | 761.4 | 763.9 | 763.9  |
| c6 + late random branch    | 742.7 | 746.7 | 747.4 | 746.7  |

Change: -15.1% (late) vs -13.2% (early): about 28 vs 21.7 cycles per
mispredict by the agent's estimate. 1-thread solves/s: not recorded.

Conclusion: branches that wait on the looked-up value cost about 30% more
per mispredict. This motivated moving the late branches earlier (p5's
regs patch, merged in 9caf0e2).

Source: scratchpad m4/neg-diag-brL-incl-c6.patch (cumulative: wip-c6 +
mk-diagbr.py L, against ff2b7a4). Recorded as two commits on ff2b7a4: c6,
then this increment; the branch's tree equals ff2b7a4 + the patch.
Numbers are the agent's own (not re-measured for this record). Not merged; recorded per the rule that every candidate gets a branch.
