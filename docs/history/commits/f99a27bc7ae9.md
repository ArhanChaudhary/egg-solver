## Original experiment record

check.sh: under qemu, the /proc/self/maps test runs alone; failed greps stop the script

qemu-aarch64 8.2 (Ubuntu 1:8.2.2) crashed now and then in the NEON library
tests with "qemu-aarch64: QEMU internal SIGSEGV {code=MAPERR, addr=0x20}".
qemu prints that when the faulting code is its own, not the guest's (outside
its generated-code buffer). It is a qemu bug: its emulation of
/proc/self/maps, read by `tables::tests::opened_table_file_is_read_only`,
races with other guest threads that map or unmap memory.

NEON library test runs under qemu (debug, CPUs 0-7 shared with builds):

| run | qemu crashes |
|---|---|
| all tests | 8/40, 11/40, 20/100 |
| one test thread | 0/30 |
| without the share tests | 2/30 |
| only the share tests | 0/110 |
| without opened_table_file_is_read_only | 0/40, 0/40, 0/40 |
| without table_meta_and_size_are_checked | 8/40 |
| opened_table_file_is_read_only alone | 0/40 |

In each of the 12 crashes looked at, that test had not finished. A 25-line
safe Rust program for aarch64 that reads /proc/self/maps 2000 times while 7
threads allocate and free 1-8 MB vectors crashes qemu the same way in 2 of
10 runs.

check.sh now runs the NEON tests without that test, then the test alone, and
checks that it ran. If qemu itself still crashes (that message, and no test
failed), the step runs once more; a test failure is never retried.

Also: `! grep -qE "FAILED|panicked" "$log"` never stopped the script (`set
-e` ignores negated commands), so those checks are now `no_failure || exit
1`. (Failed tests were still caught by cargo's exit status through
`pipefail`.)

With the series, check.sh passed 5 runs in a row on 3a9a50a (wasm steps
included, no qemu retry needed), and 5 in a row on each of 857a0c6, 8977134
and 7608a28. NEON library runs without that test: 0 qemu crashes in 120.
