## Original experiment record

m4: sibling-face masks from a table with select_unpredictable (negative, neutral -0.3%)

On the m4 stack: the face-drop mask for sibling-face pruning comes from
TABS.face_keep[f] through std::hint::select_unpredictable(f > r,
face_keep[f], !0), instead of being built from the comparison
(neg/m4-fmask-branchy-incl-c6 without the branch).

Why: no mask construction per noted value.

48 threads (bench /mnt/huge/h11 stream 20 30 48 20, capped, interleaved,
3 runs, solves/s; measured as c10u against c9, the agent's build of the
near-final m4 stack):

| build                  | run 1 | run 2 | run 3 | median |
|------------------------|-------|-------|-------|--------|
| c9 (m4 stack)          | 892.3 | 889.0 | 940.1 | 892.3  |
| c9 + face_keep select  | 889.3 | 882.2 | 937.9 | 889.3  |

Change: -0.3, -0.8, -0.2% per run (median -0.3%). Run 3 is a machine-wide
state shift that affects both builds. 1-thread solves/s: not recorded.

Conclusion: neutral. Likely the mask construction it replaces is a few
ALU ops off the critical path, while the table adds a load.

Source: scratchpad m4/neg-fmask-on-stack.patch, made on m4's stack commit
3b4fb2a; committed on 35c608c (the merged m4 stack: identical lanes.rs,
and simd.rs differs only in a comment), applied with git apply --3way.
Numbers are the agent's own (not re-measured for this record). Not merged; recorded per the rule that every candidate gets a branch.
