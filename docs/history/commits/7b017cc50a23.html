NEGATIVE (r8): Pool::run building its Worker through a Worker::new constructor (applies on top of work/r8 f99a27b, i.e. 3a9a50a + r8-share-fix).

Worker::rounds stays instruction-identical at the same address; the only other change in the binary is the share thread closure (Worker::run is inlined into it), whose stack frame shrinks from 0xfc0 + 0xf80 to 0xfc0 + 0xe40 bytes. Yet solve -c 1 at 48T (on def2cd0 + r8's fix, 4 paired holds):

random_move_17f -c 1 -n 2000.638 0.625 0.641 0.635 (median 0.6365)0.594 0.568 0.579 0.597 (0.5865)-8.0% [-9.7, -6.0]
random_state_depth17 -c 1 -n 2000.768 0.696 0.721 0.725 (0.723)0.669 0.648 0.633 0.659 (0.6535)-10.7% [-12.9, -6.9]

An earlier build with the constructor was as slow against main on 3 linker-shuffled layouts each (+5.9 to +10.5%), so it is not function order. random_state -c 1/-c 0 and bench share were neutral. The share thread's stack placement is a performance sensitivity, like the hot-code pads.
