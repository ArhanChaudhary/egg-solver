## Original experiment record

wasm: Bun instead of Node for the JavaScript tooling (Bun 1.4.4)

User request: "use bun instead of node". The tools in wasm/ now run in Bun
(1.4.4, 38afee6c8, in /data/tools/bin). The browser code stays plain web
JavaScript. No x86 code changes. The diff is wasm/*.mjs, wasm/build.sh,
check.sh, README.md, and one doc line in wasm/src/lib.rs.

- cubeopt.mjs (the entry point for both Bun and browsers) uses web APIs
  only: Worker, fetch, Blob, Atomics, navigator.hardwareConcurrency. The one
  exception is `localFile`, which turns a local path or `file:` URL into
  `Bun.file(...)`. A table file is then streamed into the module's memory,
  as a fetch or a File already were. The `node:` imports and
  worker_threads paths are gone.
- cubeopt-thread.mjs (pool worker): `self.onmessage` / `postMessage`. A
  thread that traps prints its error and ends the process with
  `process.kill` (Bun) instead of hanging.
- demo.mjs reads stdin with `Bun.stdin`.
- serve.mjs is now a `Bun.serve` static server with the COOP/COEP headers,
  the table folder at /tables/, and paths kept inside their folder.
- test.mjs runs in Bun.
- check.sh: `timeout -s KILL 300 bun wasm/test.mjs`. If bun is missing it
  skips with a note; there is no node fallback.
- The V8 warm-up (`warmUp`) is skipped in Bun. JavaScriptCore moves a
  running loop to optimized code, so the warm-up does not help there. h6, 100
  depth-17 cubes, 1 thread, paired:
  - without the warm-up: 126.5 s and 127.2 s;
  - with it: 127.0 s and 127.9 s.
  It stays for browsers: Chrome is V8, where it took the same set from
  187.7 s to 129.5 s.
- README "WebAssembly": run commands for Bun, what runs in browsers, and the
  Bun numbers next to the V8 ones.

The threads build on JavaScriptCore works with nothing changed:
- shared wasm memory with all 4 GiB imported at start-up;
- `Atomics.wait` in workers, and on Bun's main thread inside wasm (joins);
- the `_initialize` reactor init;
- the pool of threads that never exit;
- the fatal path: a minimal repro has a worker print and `process.kill`
  while the main thread blocks in `Atomics.wait`; the message shows and the
  process ends with status 143 after 0.5 s.

Stress in Bun. Each chunk ran under locked.sh (LOCK_TIMEOUT=2400) on CPUs
0-7 with 4 to 6 processes at a time; every run had a 300 s kill timeout:
- `bun wasm/test.mjs`: 200 runs before the warm-up skip and 200 after, all
  ok;
- t.mjs (threads module: h0 with 3 threads, 20 rounds of 6 share-mode
  solves and a batch): 100 runs, all ok;
- the threads demo path (`bun demo.mjs --table h4 --threads 4`, one at a
  time and `--batch`): 40 runs, all ok.
0 hangs, 0 failures.

Browsers: headless Chromium 141 against `bun serve.mjs` runs index.html
with the new cubeopt.mjs:
- 1 thread: h0 generated;
- 8 threads: h6 fetched; a random state solved in 0.63 s, the same solution
  as before.

Speed on one Zen 5 core, h6 with 100 depth-17 cubes (14.8M nodes each), 40
lanes, batch; node counts identical everywhere:

| engine              | 1 thread         | 8 threads (one L3 domain) |
|---------------------|------------------|---------------------------|
| Bun 1.4.4 (JSC)     | 126.5-127.9 s    | 33.7 s                    |
| V8 (Node 26)        | 124 s            | 40.3 s                    |
| wasmtime            | 122 s            |                           |
| native x86          | 21.7 s           | 10.65 s                   |

(With 100 cubes on 8 threads x 40 lanes, the batch's tail dominates the
8-thread times.)

Random states one at a time, 10 cubes, seed 1, mean and median per cube:

| table | Bun, 1 thread | Bun, 8 threads | V8, 1 thread | V8, 8 threads |
|-------|---------------|----------------|--------------|---------------|
| h6    | 12.2 s, 4.9 s | 1.6 s, 0.65 s  | 12.6 s, 5.0 s | 1.6 s, 0.65 s |
| h7    | 6.5 s, 2.9 s  | 0.91 s, 0.44 s | 6.7 s, 2.9 s  | 0.93 s, 0.44 s |

x86 unchanged: no source of the x86 binaries changed (the only Rust edit
is a doc comment in wasm/src/lib.rs, a crate x86 builds do not include), so
the binaries, verify.sh results and hot code are those of main 3a9a50a.
check.sh passes with /data/tools/bin on PATH: the wasm library tests under
wasmtime, and `bun wasm/test.mjs`. One earlier run hit the known scalar
Worker::release flake (r8).
