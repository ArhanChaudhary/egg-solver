share: the solver as a parameter of the visit loop

Worker::rounds loaded its &Solver from self, so LLVM had no noalias/readonly guarantee for it and reloaded the table pointer and base from the solver on every lane visit (on the dependent path to the table value) and spilled the loop index; the stream loop (run_lanes, whose solver is an argument) keeps them in registers. With the solver as an argument of rounds, the visit loop's head is the stream loop's (cargo asm: mov rax, [rbp+3512]; ...; shrx rax, [r15+8*rcx], rax with the table pointer in r15, versus a load of [r13+16] per visit). This is a share-mode-only change (lanes.rs is untouched).

Measured on 2dbe81d (opt/r7-fresh-join = main cb8cb70 + opt/l6-share-a + the r7 fresh-join fix) (h11 table; random_state = cube_solver_test dataset/random_state.txt, 500 cubes). 48 threads: paired, i.e. in each of 5 short exclusive holds every binary of the stack ran each test back to back (the machine drifts by more than these differences between holds); 1 thread: 3 runs pinned to free L3 slots. Every solution verified; bench share lengths 15:1 16:35 17:270 18:662 19:32 in every run. Values per run, and medians:
