## Original experiment record

hot: the stream and share loops start at fixed offsets of a 64-byte line

Where bench::stream_thread (the stream loop, run_lanes inlined) starts
within a 64-byte line can move 1T throughput by ~3% on this machine.
Functions are 16-byte aligned, so it starts at offset 0, 16, 32 or 48,
and the offset it gets changed with any change anywhere in the binary
(the linker places functions one after another). On main abce87c,
relinks of the same LTO object with lld --shuffle-sections seeds (3 per
offset; 1T, stream 10 60 1 24, solves/s, paired runs) gave:
| offset | abce87c               | abce87c + m7's µop stack |
|--------|-----------------------|--------------------------|
| 0      | 25.517 25.483 25.600  | 25.600 24.933 25.050     |
| 16     | 24.867 25.050 25.133  | 25.750 25.717 25.517     |
| 32     | 24.750 24.867 25.050  | 25.517 25.550 26.000     |
| 48     | 25.183 24.967 25.333  | 25.533 25.517 25.667     |
The stream_thread code of each side was byte-identical in all its
relinks. So the offset was a lottery about the size of most kernel
changes, and the best offset differs between kernels.

Now stream_thread and share::Worker::rounds each get a section of their
own (`#[unsafe(link_section)]`). `hot_section!` (new module `hot`)
starts that section on a 64-byte boundary, followed by a pad of int3
bytes. The function is the only one in its section, so it starts at the
pad's offset in every build: STREAM_PAD = 16, SHARE_PAD = 0. Checks:
- nm on 3 shuffle seeds per build: always at the pads, for every pad;
- the stream_thread code is unchanged (asm identical to main's, 1433
  lines, addresses stripped); Worker::rounds is instruction-identical
  between 1f4c85a and this base (per c10);
- without shuffling, lld places the hot sections first in .text.
The build variables CUBEOPT_STREAM_PAD / CUBEOPT_SHARE_PAD (0, 16, 32 or
48; anything else fails the build) override the pads, for re-sweeping
after kernel changes. An A/B should use the same pads on both sides, or
sweep them.

On 735dd25 the four stream pads are within the noise of each other (1T,
2 seeds per pad, against main as built): 0: +0.3 +0.7%, 16: -0.4 +0.2%,
32: -0.6 +0.5%, 48: +0.4 -0.7%. s8's loop changes made this kernel less
sensitive than abce87c's. The point of this commit is that layout stops
moving the result. It is not a speedup.

Alternatives:
- -C llvm-args=-align-loops=64 (it aligns the loops, and so the
  function): on abce87c main ran at its offset average, not its best (vs
  main at offset 0: -1.6, -1.5%; vs 16 and 32: +0.9 +0.7 +0.7%).
- nightly fn_align: not needed.

Share pad, Worker::rounds on 1f4c85a (instruction-identical here),

| pad 32            | 964.647 971.464 909.950 | 964.647 |
| pad 48            | 962.588 969.202 968.149 | 968.149 |
