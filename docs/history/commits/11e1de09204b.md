## Original experiment record

Per-child job ordering, paid only in iterations on unchanged jobs (c4)

Follow-up of opt/childorder (per-child statistics, two-part iterations;
-4..6% nodes but neutral throughput), reworked so that the node reduction
turns into throughput:

- Each job keeps an 8-bit statistic per root child (`Job::ck`, quantized
  sum of the lookup terms of the child's subtree in the last iteration,
  +1 step for children on faces 1, 3, 5, as solver's face weight: -0.3%).
  Job roots always branch on the normal side, so the statistics refer to
  the normal side's children for every job (free side choice with
  whole-job ranking of inverse-side jobs: -4.2% nodes instead of -5.7%;
  nodes/s are the same either way).
- An iteration right after the jobs were extended runs whole jobs by
  decreasing inherited statistic (each new job's is its parent's child's).
  The entries are prepared in `extend_jobs` when a job's bounds resolve
  (its line is still cached); no sort pass over the jobs.
- An iteration on the same jobs as the previous one (with h11: T >= 18, the
  likely last ones; every such iteration but the last is exhaustive, where
  order does not matter) is split: first one entry per candidate child (ck
  above a sampled threshold, ~3 per job), built branch-free with an
  AVX-512 compress and counting-sorted by ck; a run's group (the job's
  not-yet-run candidates at most one octave below) is formed only when its
  entry is reached (most entries are never reached in the last iteration);
  then each job's remaining children, job by job.
- Job bookkeeping kept cheap: the current job is copied into the lane at
  setup and written back with one 32-byte store at the end of the run
  (piecewise stores followed by a 32-byte load stalled on store
  forwarding); X values (`Job::tw`) packed with pdep/pext; runs over all
  of a job's children skip the X'-needs-X and face-pruning bookkeeping;
  prefetch of the jobs of the next entry and of one 4 ahead.
- The job-end path (`next_run`: finish, set up the next run or iteration)
  is out of line and #[cold]: inlined, or merely out of line, the search
  loop got extra spills (2-3% fewer nodes/s on ff2b7a4).

Soundness: in every iteration, every (job, normal-side child) runs exactly
once, except children whose root an earlier run of the job proved (lb) or
whose face it pruned (both imply no solution of the remaining length
through them); targets rise one at a time, so the first solution found is
optimal. An X' child runs with its X sibling or with X's other-side value
recorded in the job (position-only, valid across iterations), and is in
`skip` iff that value prunes it. Covered by a unit test that drives the run
machinery over random jobs with simulated outcomes for several iterations,
and by a debug assertion at the end of every iteration.

Throughput, 48 threads (bench stream 20 30 48 20, interleaved, solves/s):

| build          | run 1 | run 2 | run 3 | run 4 | run 5 | median |
|----------------|-------|-------|-------|-------|-------|--------|
| main 35c608c   | 920.6 | 944.4 | 926.7 | 898.5 | 902.1 | 920.6  |
| c4             | 948.2 | 938.2 | 907.5 | 893.3 | 889.1 | 907.5  |

Median -1.4%; per-run ratios +3.0, -0.7, -2.1, -0.6, -1.4% (mean -0.4%).
Four further paired stream runs: 899.2/897.6, 893.7/890.9, 902.0/893.3,
902.3/904.2. On 35c608c this is neutral: the stream needs 6.6% fewer
nodes, but nodes/s are 6.9% lower (2764/2743/2748/2784 M vs main's
2964/2942/2971/2969 M): job bookkeeping outside the search loop is 6.3%
of samples (setup_job 2.5, start_iteration 2.75, next_run 1.1) vs ~3.9%
for main, and the search loop itself costs ~4% more per node. (On
ff2b7a4 the same code measured +1.6..+3.4% in paired runs, the search
loop then matching an earlier variant's; the M4 loop is faster, so the
fixed costs weigh more.)

Memory: peak RSS 2.76 GB (random:3000 batch; 3.03 GB on a stream run)
vs 1.08 / 1.50 GB for main: 32-byte jobs (1.4 MB per lane at 43K jobs)
plus u32 run entries (~0.5-0.7 MB, and as much scratch).

Verified: check.sh; lengths 18:100 on depth18; 400 random cubes with
debug assertions (including the end-of-iteration coverage check).
