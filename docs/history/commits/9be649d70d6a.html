Original experiment record

share: a first pass reports no longer solution while it reports its shortest one

Root cause (a real race, since 085a9fd's first pass): phase_done takes the pass's candidate (a solution of phase q) from PassState when the phases below q have ended, releases the pass lock, and only then sets the cube's done (report_pass). In that window a lane still running an entry of a later phase p > q can find a solution: one whose thread has not yet dropped it (cancel_done runs once per round), or a donated piece (piece does not check pass_limit). found then saw an empty candidate and p <= phases_ended (phases q..p-1 had ended by their drops), and reported it at once. Whichever done.swap won was published, so a release build could report a non-optimal solution, one or more moves too long.

Fix: PassState keeps the phase of the shortest solution found (shortest, phase + 1, 0 for none) also after the candidate is taken, and a solution of a phase as high is of no use. The decisions move to PassState::offer and PassState::ended; found and phase_done keep the lock and report as before. (shortest keeps the derived all-zero default of PassState: the code that makes a cube in Worker::fresh is unchanged.)

A note in Pool::run (code unchanged): building the worker through a Worker::new there, for the tests, shrank the share thread's stack frame by 320 bytes with rounds unchanged, and took solve -c 1 at 48T on random_move_17f from 0.587 to 0.637 ms and on depth-17 states from 0.654 to 0.723 ms (4 paired holds, also across 3 linker-shuffled layouts). The tests build their workers with a helper instead.

Regression test: first_pass_reports_no_longer_solution_while_reporting_one drives one worker by hand, in one thread. Its lane runs an entry of phase 2 after phases 0 and 1 ended, another thread has taken a solution of phase 1 to report it, and the lane finds a solution. On main it fails ("a longer solution was reported"); it passes now. (hand_worker, take_next, run_up_to_phase and first_pass_cube are test helpers; miri.sh runs the first_pass_ tests with one seed, about 5 minutes.)

How likely it was: not seen in any run. Oversubscribed stress, 192 threads x 24 lanes on 48 cores plus 48 busy loops, solve -c 1, lengths against stream-mode references and known depths (short 1-14 moves 1000, random_move_15f/16f 500 each, random_state_depth15 433, depth16 1361, random_state 500): 0 longer on 857a0c6, def2cd0, 8977134 and 7608a28, also with the take-to-report window widened to 500 us. With a 20 ms window and a log of every real race event (a direct report of phase p while a phase-q candidate, q < p, was taken and not yet reported): 0 events in 3794 cubes. When the window opens, the higher phases' lanes were dropped by their threads long before, and pieces end within microseconds with h11.

Other report paths checked (no early report found): iterations outside the first pass report at once, which is sound because iteration T is built only when T-1's outstanding count reaches 0 (an uncounted claim can only keep it high); pieces and local splits carry their phase and target and are counted in outstanding and phase_left while the donor's job is pending; symmetric-start builds only change the job list, which all phases share; pass_limit is below its maximum only while a candidate exists, which is always reported; def2cd0's split iterations count runs, every (job, root child) is in exactly one run, X and X' stay together, and a split iteration is never a first pass.
