DIAGNOSTIC (not for merging): counting global allocator in bench and solve

perf book "Heap Allocations" and "Alternative Allocators": do allocations matter here? A #[global_allocator] wrapper around System counts allocs, reallocs, bytes and allocations of >= 128 KiB, printed per run (ALLOC line on stderr). valgrind's DHAT cannot run the AVX-512 build.

Per cube on main 7608a28 (1T bench slots; solve with 2 threads):

runcubesallocsreallocsbytes>= 128 KiB
bench stream 5+30 s, 1T, 24 lanes8509.93.3888 KB2.2
bench share random:500:2026, 1T5005.73.0432 KB1.0
solve -t 2 -c 1, random_state 10010025.73.1106 KB0.22
solve -t 2 -c 0, random_state 30030025.23.0245 KB0.57
solve -t 2 -c 1, random_move_15f 30030021.92.140 KB0.06

strace -f -c over a whole 1T stream run (5+30 s): 25 mmap, 14 munmap, 6 madvise, 267 mprotect, 4 brk; share 1T 300 cubes: 117 memory syscalls in all; solve -t 2 -c 1 100 cubes: 113, plus 101 writes (one per cube). perf stat: 24.8K page faults per 1T stream run, nearly all at start-up. The 1T cpu-clock profile has 0.03% of samples in libc (malloc, free, memset, memmove together). Conclusion: no allocator or buffer-reuse change can gain measurably (not timed).
