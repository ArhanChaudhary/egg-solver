## Original experiment record

gen: hashbrown's HashSet for the dfs prefix set

The DFS generator (gen/dfs.rs: k = 1..10, and 0 with --dfs) prunes each
root's children that are in the BFS prefix's last two levels (7.4M h11 entries
at prefix depth 8): one set lookup per child of a root, ~13 per root and
pass. The set was our own open-addressing one (linear probing, at most
half full: 16M slots of 8 bytes, 128 MB, a cache miss per lookup). It is
now hashbrown's HashSet (its default hasher, foldhash), presized:
16M buckets plus 16 MB of control bytes, and a lookup that misses is
mostly answered by one 16-byte group of control bytes, which are 1/8 of
the slots' size. Micro-benchmark (d1-x/hashbench, 8M random 40-bit
entries, 20M lookups, 1/3 hits, 1T): 24.3 -> 12.2 ns per lookup; building
the set 126 -> ~150 ms.

The crates.io hashbrown, not std's HashSet: an FxHashSet (std's HashSet
with rustc-hash, which the user suggested) is as fast here, but it shares
std's hashbrown code with symstart's HashMap, and LTO then compiled
Lane::extend_jobs and bench's thread closure (the stream loop's caller,
frame 0x700 -> 0x740) differently (neg/d1-fx-dfs). With this crate every
cubeopt, bench and solve function outside gen is the same code as before
(addresses and call targets stripped): the stream and share hot paths
and frames are untouched, so only generation is measured.

Generation (gen K BASE OUT -t 8 on one 8-core L3 slot, shared lock;
compute = the prefix and pass times from gen's log, without the file
write, whose time varied 0.1-5 s with the disk; outputs byte-identical,

The gain is the set's share of the work: about 13 lookups against
13.3^(base + 2 - 8) leaves per root and pass. It is large for small bases
(base 7-8, k = 0..3), and small for the big tables (base 10: 31K leaves per
root in the last pass).
