## Original experiment record

c4: cap the first-part runs per job (negative, +1.88% / -4.26% vs -5.74% nodes)

In c4's split iterations, cap the number of first-part runs per job:
- g1: one run per job (its best children within MERGE); the job's other
  candidates wait for the second part;
- g2: at most two runs per job, the second with all remaining candidates.

The code is already in c4's WIP commit cb30999 ("WIP v8"), behind
experiment knob 7 in build_runs. The agent's saved patch is only a hunk
fragment without file headers, so it cannot be applied; it is committed
here as negatives/group-caps.patch on cb30999. To reproduce, build
cb30999 and run with C4X=-1,-1,-1,-1,-1,-1,-1,1 (g1) or
C4X=-1,-1,-1,-1,-1,-1,-1,2 (g2).

Why: c4 wanted to make the build-time grouping branch-free.

Nodes/cube (bench random:N:SEED N 48 20; combined = all 4000 cubes):

| config                               | 1000:2026         | 3000:777          | combined |
|--------------------------------------|-------------------|-------------------|----------|
| main                                 | 3295521           | 3249811           |          |
| g1: one run per job                  | 3360800 (+1.98%)  | 3309584 (+1.84%)  | +1.88%   |
| g2: at most two runs per job         | 3172120 (-3.74%)  | 3105542 (-4.44%)  | -4.26%   |
| default: one run per MERGE window    |                   |                   | -5.74%   |

48-thread and 1-thread solves/s: not measured.

Conclusion: both caps cost nodes; g1 is worse than main. Likely a job's
later candidates are often among the iteration's best and must not wait
for the second part. Run-time grouping (c4 v9) later made the build-time
grouping cheap, so the cap was moot.

Source: scratchpad c4/neg-group-caps.patch (header and fragment only);
the code is knob 7 of cb30999.
