share: parking_lot's Mutex for the share mode's mutexes

The share mode's mutexes (a cube's result and first-pass state, the free lists of buffers, the counters and the trace text) were std's Mutex, each lock followed by .unwrap() or .unwrap_or_else(PoisonError::into_inner). parking_lot's Mutex has no poisoning, so there is no poison flag to check on the guard's drop and no panic path per lock, and its lock word is one byte; uncontended, both take one CAS to lock and one to unlock. The code around the locks shrinks and inlines differently: the share thread closure (solve's, with Pool::run and Worker::run inlined) 4310 -> 3969 bytes, its frame unchanged (0x1f40); take_bufs is now inlined; Worker::rounds and bench::stream_thread unchanged. Only type and call-site changes (the pass mutex included: ctx.pass.lock() instead of ctx.pass.lock().unwrap()).

Native targets only. On wasm, parking_lot_core parks threads only with its nightly feature (all(feature = "nightly", target_family = "wasm", target_feature = "atomics")); on stable Rust its wasm parker panics ("Parking not supported on this platform") as soon as a lock is contended, which the threads build hit in wasm/test.mjs. So on wasm Mutex is a small wrapper of std's Mutex with the same lock() (the guard, poisoning ignored, as with parking_lot), and parking_lot is a dependency only for non-wasm targets. The native code is the same as with parking_lot everywhere.

On 585b3b6 and later (r8's PassState::offer/ended at the pass sites): the share thread closures (solve 3969 bytes, bench::share_thread 3972, frames 0x1f40) and Worker::rounds are the same code as in the measured build; only the functions with r8's code differ from it (found, maintain, and end_job and continue_local, which inline phase_ended).

Search identical (verify.sh on the whole series: nodes/cube 3058198 lookups/cube 2588380, lengths 15:1 16:35 17:270 18:662 19:32; 3644301 3084160, 18:100); no bad solutions. Measured at least as fast: bench share +0.8% at 48T (7 of 8 pairs ahead) and +1.3% at 1T (6 of 6), -c 1 latency at 48T within noise (median pairs -1.4%, -0.8%, -0.3%).
