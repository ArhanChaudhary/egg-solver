Original experiment record

b2: read ahead the next lane's lookup value (negative, -4.4%)

During a lane's visit, the run loop also reads the next lane's pending lookup value into that lane's state (read_ahead: k_v, plus whether it prunes the pending child). The next visit's prune branches then depend on a byte in the lane state instead of on the table load. Includes a branchless value() for values read ahead of use, and padding that puts the bytes in separate 4-byte slots.

Why: a mispredicted branch that waits on a DRAM load resolves late and costs more; reading the value one visit early should make the prune branches resolve early.

48 threads (bench /mnt/huge/h11 stream 20 30 48 16, solves/s, 1 run each):

buildsolves/schange
main fe58740671.8
read-ahead, padded (this patch)641.9-4.4%
earlier session, main fe58740683.5
first version (ra), unpadded624.5-8.6%
ra2 (+ precomputed prune), unpadded623.8-8.7%

1-thread solves/s: not recorded.

Conclusion: slower. The unpadded versions also hit a store-to-load forwarding stall (LLVM widened the k_po byte load to 32 bits across the phase byte just stored, 5% of samples); padding fixed that and it is still -4.4%. Likely reason: b2's sensitivity builds showed the lookup latency is already hidden by the interleaved lanes (+12 cycles of latency cost only what its extra uops cost), so resolving the prune branches earlier saves little, while the read-ahead adds a load and stores of a second lane's state to every visit.
