## Original experiment record

Use cube48opt's table layout: E-slice placement innermost, 16-byte groups

Index X = ((class*70 + msplit) << 20) | (eo11 << 9) | eslot, hk index
((X >> (11-k)) & !0x1FF) | (X & 0x1FF). Rows of 512 2-bit slots (128
bytes); each 16-byte group holds 62 E-slice placements and a 4-bit group
minimum (slots 0-1). The fallback for code 0 entries now forgets only part
of the E-slice placement instead of ~8 bits of edge orientation.

Table size for h11 grows from 56.5 GiB to 58.0 GiB.

Benchmark (./bench.sh: 1000 random states, 48 threads, h11 base 10):

| version         | solves/sec | nodes/cube | ns/node/thread |
|-----------------|-----------:|-----------:|---------------:|
| main (ec7e133)  |      143.4 |      8.58M |           38.9 |
| this branch     |      144.5 |      8.65M |           38.4 |

Neutral at h11 (code 0 is only 0.5% of h11 entries), but much stronger
for smaller tables: h0 on 100 depth-15 states drops from 72.0M to 21.1M
nodes/cube (22 -> 66 solves/sec).
