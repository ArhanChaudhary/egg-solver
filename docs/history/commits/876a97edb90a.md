## Original experiment record

wasm: the WebAssembly module (wasm/) for browsers and Node; README "WebAssembly"

User request: "make it also compile to wasm". `wasm/build.sh` builds two
modules of ~380 KB each:
- `wasm/dist/cubeopt.wasm`: wasm32-wasip1, one thread;
- `cubeopt-threads.wasm`: wasm32-wasip1-threads.

- wasm/src/lib.rs (crate cubeopt-wasm, a workspace member, cdylib): a plain
  C ABI, no bindings generator. The exports:
  - `cubeopt_table_buffer(len)` returns memory that the caller fills with a
    table file; `cubeopt_table_load(verify)` checks and installs it;
  - `cubeopt_generate(k, base, threads)` (h0..h6);
  - `cubeopt_solve`: one cube, in share mode with one cube in progress, on
    this thread or on all threads;
  - `cubeopt_solve_batch`: stream mode, for throughput;
  - `cubeopt_bench`: as `bench stream`;
  - `cubeopt_random`: the facelets of the cubes of `bench random:N:SEED`.
  Cubes are scrambles or facelet strings. Results come back as JSON in an
  output buffer. All exports share one compiled copy of the stream search
  (`stream`), and the build script sets cfg(wasm_threads), because the
  threads target's `atomics` is not visible to cfg(target_feature).
- Lanes per thread in the module: 16. Lanes pay off in wasm too, but
  already fully at 8. V8, h6, 100 depth-17 cubes, 1 thread:

  | lanes    | 1     | 8     | 16    | 24    | 40    | 64    |
  |----------|-------|-------|-------|-------|-------|-------|
  | time (s) | 200.6 | 123.8 | 125.3 | 128.2 | 130.3 | 127.9 |

  16 lanes take 23 MB instead of the 56 MB of 40.
- wasm/cubeopt.mjs: the JavaScript API, for Node and browsers. It:
  - instantiates the module;
  - provides the WASI functions the module imports (clock, console output,
    sleep);
  - for the threads build, implements wasi-threads' `thread-spawn` with a
    pool of workers (`cubeopt-thread.mjs`, Web Workers or worker_threads).
    A worker waits on a shared control slot, runs `wasi_thread_start`, and
    waits again;
  - copies tables from the file or fetch stream straight into the module's
    memory;
  - warms up V8 (`warmUp`, called by loadTable and generateTable). V8 runs
    new code with its baseline compiler and gives a function optimized code
    only from its next call, so a long first solve would run slowly to its
    end. On h6 with 100 depth-17 cubes and 1 thread:

    | Node 26 run          | time (s)            |
    |----------------------|---------------------|
    | default, no warm-up  | 187.7               |
    | with the warm-up     | 129.5               |
    | `--no-liftoff`       | 130.6 (same module) |

    The warm-up takes ~0.6 s.
- The demos:
  - wasm/demo.mjs (Node): solve stdin or random states, `--batch`,
    `--bench`;
  - wasm/index.html + demo-worker.mjs (browser): generate h0..h4 or load a
    table file or URL, then solve scrambles, facelets or random states;
  - serve.mjs: a static server with the COOP/COEP headers the threads build
    needs, and a table folder at /tables/;
  - test.mjs: a smoke test of both builds, run by check.sh when node is
    installed (h0 generated, solutions checked, threads present).
- [profile.wasm-release]: release without debug info, for the module's
  build.
- README.md "WebAssembly": build, JS API, Node, browser, tables per
  environment with measured solve times, threads and COOP/COEP, speed,
  memory64, tests.

  h7 (3.6 GiB) fits in wasm32's memory: loading it with `verify` takes 23 s.
  The node counts are identical to native (previous commit; h5 and h6).

  serve.mjs:

    0.66 s instead of 5.15 s on 1 thread (same solution).
