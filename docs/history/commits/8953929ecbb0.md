## Original experiment record

tables: check the table meta and the file size when opening a table

`read_meta` parsed the meta file with `unwrap` and indexing (a panic on
a malformed file) and took `k` and `base` as they came (`base` truncated
to u8). The search relies on both:
- bounds are below 16 (`assert_unchecked(po < 16 && pm < 16)` in
  `Lane::resolve_moved`, the 16x16 `heur_pair` table): a base above 12
  makes `base + 3` reach 16, which is undefined behavior there;
- the index layout of `k` (`Solver::row_mul`, `eo_mask`): a meta of
  another `k` than the file's (e.g. a stale `tables/*.hugemeta`, which
  is found through the source tree the binary was built from) gives
  indices into the wrong layout, i.e. wrong and possibly too high bounds,
  so silently non-optimal solutions.

Now `read_meta` returns an error unless the file holds exactly `k <= 11`
and `base <= 12`, and `H48Table::open` returns an error unless the table
file is at least the size of an h`k` table and less than 1 GiB larger
(hugetlbfs files are rounded up to whole pages; the tables in
/mnt/huge and /data/tables pass).

Test `table_meta_and_size_are_checked`: valid meta, bad metas (base 13,
k 12, missing or extra fields, not numbers) and a file of the wrong size.

Not on a hot path: no change to the search.
