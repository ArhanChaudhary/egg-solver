Original experiment record

solve: share workers' state and frames and the round loop at fixed page offsets

r8 found that building the share Worker with Worker::new instead of a struct literal made solve -c 1 8% slower at 48T, with Worker::rounds byte-identical at the same address. The cause is the placement of stack data within a 4 KiB page. This commit fixes solve's share-mode placement at main's current offsets, so -c 1 is unchanged by construction. Edits to callers, std, TLS, or anything that grows .rodata or .eh_frame (such as u1's CLI crates) can no longer move it. bench is untouched: its .text, .data, .data.rel.ro and .eh_frame are byte-identical to main's.

Mechanism (tools and sweeps on neg/s9-placement-sweep)

  • Zen 5 has 4K aliasing. A load waits behind an older in-flight store that matches it in address bits 11..0 but lies in another page. In a pointer chase with one store per iteration, where both addresses resolve together, each load took 6.07 TSC ticks instead of 2.44 when the store overlapped the load's bytes mod 4096. There is no penalty when the store address is known early.
  • A thread's stack starts at a fixed page offset, so the page offsets of a worker's frames, its Worker and its round counter were sums of frame sizes. r8's fix3 (gdb) enters rounds at 0xf78 instead of 0xe38 and keeps the round counter at 0xec0 instead of 0xe68, with the Worker (0x040) and the lanes heap (0xac0) unchanged. Remeasured: 7.4% / 6.1% slower wall/cube on 17-move / depth-17 scrambles at 48T.
  • Runtime pads on one binary: fix3's Worker and rounds offsets alone are not slow. So the colliding pair involves the thread function's own frame, most likely the round counter (stored every round) against its callees' frames. On 7608a28, whole-thread pads over 64 offsets moved -c 1 by -1.1..+0.9% per cube. But two other layouts were slower on 17-move -c 1:
    • rounds at the page top, Worker and round counter both at page offset 0x180: +0.3 +5.7 +9.0% wall, 3 holds;
    • the same with rounds at 0xe38: Worker and counter both at 0xec0. Some layouts are bad, and without a pin any edit can land on one.
  • Code: .text starts after .eh_frame, which grows with every new function, so the round loop's page offset moved in 64-byte steps with unrelated edits.

Change

  • Pool::run_pinned (share.rs) is a copy of run; solve uses it through solve_all_pinned. It moves the Worker to byte 0x040 of a page-aligned stack slot (PinnedWorker, repr(align(4096)): the compiler realigns the frame). It then runs the worker from a frame WORKER_DEPTH (384) bytes deeper, so rounds is entered at page offset 0xe38. Both are main's values (gdb); the round counter is at 0xe48, main 0xe68. run itself is unchanged, so bench's code is too.
  • .text.hot_share is page-aligned from solve.rs (a binary's module asm comes before the library's 64-byte pad), so rounds starts at page offset 0x310, as on main.
  • On x86-64 Linux only; elsewhere run_pinned runs the worker directly.
  • Why not bench. Pinning its stream loop and helpers at page offsets lost 1T stream against main in every variant (neg/s9-full-pin: 10 offsets of the loop gave -0.1..-1.4%; with main's helper offsets, -0.3..-1.3%), while bench share gained 1.5..2.2%. Main's stream layout seems to be a good one that page offsets alone don't reproduce, so bench is left as it is.

48 threads, solve -t 48 -c 1 -n 300, ms per cube (wall/cube; lower is better). 8 paired exclusive holds of main (0d1a0e8, before) and this commit (after), back to back in alternating order. My waiters ran at SCHED_IDLE.
