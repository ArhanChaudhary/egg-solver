## Original experiment record

m4: job-finished path out of line (negative, -1.7%)

On the m4 stack: the job-finished path of advance (store the job's
statistic, setup_job, start_iteration on the last job) moves into an
#[inline(never)] next_job.

Why: a smaller hot loop.

48 threads (bench /mnt/huge/h11 stream 20 30 48 20, capped, interleaved,
3 runs, solves/s; measured as c9n against c9, the agent's build of the
near-final m4 stack):

| build                  | run 1 | run 2 | run 3 | median |
|------------------------|-------|-------|-------|--------|
| c9 (m4 stack)          | 892.3 | 889.0 | 940.1 | 892.3  |
| c9 + next_job out of line | 877.0 | 875.2 | 923.6 | 877.0  |

Change: -1.7, -1.6, -1.8% per run (median -1.7%). 1-thread solves/s:
not recorded.

Conclusion: consistently slower. Likely the call boundary forces the lane
state into memory around every job end, and the loop gains nothing from
being smaller. c4 saw similar layout effects with #[cold] on its
next_run.

Source: scratchpad m4/neg-nextjob-on-stack.patch, made on m4's stack
commit 3b4fb2a (lanes.rs identical to 35c608c's); committed on 35c608c,
applies cleanly.
