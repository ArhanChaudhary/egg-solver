share: cancel_done counts down the jobs it leaves with nothing pending (release flake)

The flaky debug_assert!(loc.pending == 0 && loc.claimed == 0) in Worker::release (share tests in debug builds: share_first_pass_reports_ the_shortest_solution, share_protocol_with_tiny_search).

Root cause: since 9e69243, cancel_done ends and deactivates the dropped lanes and refills them together. Before, each dropped lane's restart(i, Some(slot)) went through continue_local, which settles the slot (counts its finished jobs down from the cube's outstanding); now only release_done settles, and only for solved cubes. A first pass's entries dropped as useless (pass_limit: a solution as short was found, 085a9fd) belong to a cube that is not solved yet. When they were the last pending jobs of a thread's share of the cube, its claimed count stayed uncounted until the thread came back to that slot or the cube was solved and release_done ran. If the pool finished first, Worker::run's exit loop released the slot with the count still there.

Evidence: on main, an instrumented build caught both of its failures as such a slot (dropped by cancel_done for pass_limit 6 while the cube was not done; at the release the cube was done, and claimed == outstanding: 5619 and 12936, i.e. this thread's count was all that was left). Bisect, 30 debug runs of the two tests each: 735dd25 0, 33ca449 0, 085a9fd 0, 1f4c85a 0, 9e69243 6, 5cce44d 2.

In release builds it was harmless: an uncounted claim keeps outstanding too high, never too low, so no iteration ended early and nothing was counted twice (the count is subtracted once, by the slot's next settle). It could only hang an iteration whose end depended on outstanding, but pass_limit is below its maximum only while the pass has a candidate, and that candidate is reported (phase_done) when the lower phases end, which phase_left and phase_pending count on every end, apart from outstanding. A solved cube builds no more iterations, and a later iteration cannot start without the count.

Fix: after its drops, cancel_done settles every slot (cold: once per solved cube or new pass candidate). The invariant is checked in debug builds where a count left behind would matter: counted_down (every cube with nothing pending here has its jobs counted down) at the end of maintain and when a thread runs out of lanes (idle_wait), besides release.

Regression test: first_pass_dropped_entries_are_counted_down drives two workers by hand, in one thread: the first runs an entry of phase 0, the second an entry of a later phase after it ran and claimed all the others; a solution of that phase is found, and the second worker's maintain drops its entry. On main it fails ("dropped entries left outstanding"); it passes now, and the cube is reported once phase 0 ends, with nothing outstanding.
