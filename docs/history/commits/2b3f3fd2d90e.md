DIAGNOSTIC (not for merge). Against cb8cb70 (= fc6d9c9's tree).

The visit loop passes the pending value through three dependent `imul
x, x, 1` (asm, 9 cycles) before the dispatch, so every prune branch of
the visit resolves 9 cycles later. The control build (branch
m7-dnolat, not attached) runs the same three imuls on `l.cube_index`,
off the chain. Search unchanged.

1T, all three built in the same folder (3 concurrent runs in separate
L3 slots, stream 10 60 1 24, solves/s):
| build                      | runs                 | median |
|----------------------------|----------------------|--------|
| main                       | 24.533 24.400 24.767 | 24.533 |
| +9 cycles on the value     | 23.483 22.883 23.300 | 23.300 (-5.0%) |
| same imuls off the chain   | 24.050 23.883 24.250 | 24.050 (-2.0%) |

So the latency costs about 3.1% (on-chain vs off-chain), roughly 0.35%
per cycle of value-chain latency. Removing it with a read-ahead costs
more than it saves (neg-read-ahead, -3.3%). The control's -2.0% for
three off-chain instructions per visit also shows that the visit loop
is sensitive to added work, not only to latency.
