## Original experiment record

NEG share: sort_unstable_by for the trace's finish times (+7.6 KB bench .text)

The clippy/perf-book idiom "sort_unstable where equal elements are
indistinguishable", at its one library site: trace_iteration sorts the
threads' finish times (at most 48 f64, behind CUBE_TRACE) with
sort_by(f64::total_cmp). total_cmp is a total order on the bits, so the
unstable sort gives the same result.

Rejected (no gain, code growth); measured on main ca820b6, same folder,
objdump:
- bench: .text 508666 -> 516314 bytes (+7,648). bench.rs keeps
  `times.sort_by(f64::total_cmp)`, so the stable f64 sort stays and a second
  instantiation is added (quicksort 5875 B, heapsort 626, insertion sort 622,
  ipnsort 496, median3 206).
- solve: .text 458602 -> 457290 (-1,312; its only f64 sort was this one).
- bench's hot loops move by +0xc0 within their page (stream_thread page
  offset 0x610 -> 0x6d0, Worker::rounds 0x1d0 -> 0x290). Their instructions,
  64-byte line offsets and frames are unchanged.
The sort runs once per iteration, only with CUBE_TRACE set, on <= 48 values.
Not timed.
