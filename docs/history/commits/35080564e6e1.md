## Original experiment record

b2: read-ahead with the resolve bookkeeping and a unified dispatch (negative, -8.0%)

Extends the read-ahead (neg/b2-readahead-value, included here): the
resolve bookkeeping (noting the value, the prune decision) moves into the
read-ahead, and the phase dispatch is replaced by a prune-first unified
dispatch (ra5, padded).

Why: once the value and the prune decision are known a visit early, the
visit itself should need only one well-predicted branch.

48 threads (bench /mnt/huge/h11 stream 20 30 48 16, solves/s, same run,
1 run each):

| build                                 | solves/s | change vs main |
|---------------------------------------|----------|----------------|
| main fe58740                          | 671.8    |                |
| read-ahead value only (ra2p)          | 641.9    | -4.4%          |
| + bookkeeping, unified dispatch (ra5p)| 617.7    | -8.0%          |

Cachegrind of ra3, the bookkeeping step before the dispatch change
(unpadded; x86-64-v3 build, random:16:2026, 1 thread), per node:

| build | instructions | branches | mispredicts (cachegrind model) |
|-------|--------------|----------|--------------------------------|
| main  | 211.2        | 17.8     | 2.11                           |
| ra3   | 243.2        | 20.3     | 2.15                           |

1-thread solves/s: not recorded.

Conclusion: slower than the value-only read-ahead. Moving the bookkeeping
adds about 15% instructions and branches per node without removing
mispredicts, and the phase dispatch it replaces is predicted well on real
Zen 5 hardware (removing it lost in every b2 experiment, see
neg/b2-unified-resolve).

Source: scratchpad b2/neg-readahead-bookkeeping-dispatch.patch
(= wip-readahead5p), made against fe58740; applies cleanly.
Numbers are the agent's own (not re-measured for this record). Not merged; recorded per the rule that every candidate gets a branch.
