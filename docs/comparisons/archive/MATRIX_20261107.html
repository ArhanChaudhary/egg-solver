egg-solver is the Rust project previously named cube-opt / cubeopt. Run IDs that begin with cubeoptrs are egg-solver runs. cubeopt30 and cube48opt10 are separate prebuilt competitors and have their own rows.

The comparison measurements use commit 979dcf6. The later renamed source is a247321cffefb4683ff73206d1b6f17863589cb4; its full native/scalar/ARM/WASM checks, hot-code comparisons and legacy h8 search verification passed. Final h11 identity and performance comparisons are complete; their results are below. The ordinary nissy h7–h11 comparisons are retained. The distance-20 rows that failed the interference check were replaced by serial reruns.

Accepted measurement records: 551. Required report cells complete: 230/230 (100.0%). Percentages count complete cells; partial distance-20 samples do not produce aggregate headline timings. All times exclude table generation and loading. Table sizes use decimal GB; page sizes use GiB/MiB. Hardware-counter measurements are a separate dataset from the portable phack kit and are not part of these VM timing tables.

This document includes both page types, 1T/48T, latency/batch/stream semantics, wiki metrics, complete distance-20 samples, build screening, fairness qualifications, and the complete coverage ledger below.

egg-solver: commit 979dcf6 (merge of the command-line interface work: clap, anyhow, thiserror, log/env_logger, --json, indicatif, clap_complete, criterion). Machine: AMD EPYC 9V45, 48 cores (Zen 5), 94 GiB; THP enabled=madvise, defrag=madvise. Harness: cube_solver_test runtest.sh (extended), driven by final-compare.sh.

Cells: seconds per cube (sec/solv); at 48T the median over repeats [min-max, repeats]; at 1T (one run of 50 cubes, or two 25-cube chunks) ± the 95% interval of the mean over the cubes (this is the cube-to-cube spread; every solver gets the same cubes, see 'per cube' in the headline). 1G = 1 GiB hugetlb pages, THP = 2 MiB transparent huge pages: every solver is measured on both, and a speedup is only stated between equal page types, equal semantics and the same size group. 'size' is the table size relative to the egg-solver table it is compared with. GB·s = table GB x sec/solv at 48T. nodes/cube is each solver's own count (not comparable across solvers).

No-panic integration: in first-party sources (dependencies excluded), the same source scanner found 127 forbidden explicit calls at 1f5eb70 and zero at 01e7683 (including shipped backends, binaries and build scripts; tests and compile-time contexts excluded). The full backend checks enforce the policy. Source inventory and remaining implicit-check diagnostics.

Miri checks the executions and schedules exercised by the tests; it does not prove safety for every input or interleaving.

The initial optional strict-provenance attempt stopped at pointer tagging in parking_lot_core 0.9.12 (word_lock.rs:320, seed14): an unsupported operation in that mode, not a reported undefined-behavior finding. The accepted runs use default provenance handling, retain the pointer-cast warnings, and keep aliasing, alignment, bounds, validity and race checks enabled. The original diagnostic is preserved separately.

A subsequent run rejected parking_lot_core 0.9.12 Linux futex c-variadic pointer arguments under seed15. The production dependency contains a minimal backport of upstream explicit raw-pointer conversions; the accepted Miri runs use that same dependency source.

Distance-20 positions (cube20.org)

Positions from the known list of distance-20 positions at https://cube20.org/distance20s/ (list of 25 July 2025; random samples of 10 and 100, converted to the harness format). Every position is a proven distance-20 position in the half-turn metric: a solver must exhaust depth 19 before it finds a 20-move solution, so these are the hardest cases. 1 GiB pages only; chosen builds. 48T: the 100-cube sample, one run per solver (chunked into holds of <= 15 min where needed: the per-cube times and, for nxopt/vcube, the harness formula sum / cubes / 48 do not depend on the chunking); 1T: the 10-cube sample for every solver (and the 100-cube sample for egg-solver where cheap). Semantics as above: latency rows (all threads on one cube) vs throughput rows (one cube per thread).

1T method: to fit ~10 h of 1T work, the 1T rows ran in parallel blocks, each inside one exclusive machine hold: up to 5 of these 1T rows at once, one per L3 domain (CPUs 8-15, 16-23, 24-31, 32-39, 40-47; CPUs 0-7 left to the harness), every row next to 4 busy neighbours (idle slots ran an unreported filler, egg-solver h8 on random states). (Threshold: > 2% would have meant serial 1T rows for that solver. Failed families: h48; their parallel timings are excluded and replaced by serial reruns.)

A timing cell is shown only when all 10 or 100 requested cubes are present. Probes and incomplete chunks are withheld from timings and speedup claims.

Harness correction (2026-11-05)

Every 48T row measured before 06:45 on 2026-11-05 used a shell page sampler that forked pgrep/awk/cat every 0.1 s (later 2 s) at the solver's own priority. With all 48 cores busy, each fork preempted a worker thread. It made egg-solver's 1 GiB latency rows 11-27% slower at 48T: those runs map their table instantly, so the whole solve fell in the dense sampling window, while the THP rows spent that window copying the table (sys time 17-31 s against 6 s). This produced the "1 GiB slower than THP" result in the provisional rows; measured cleanly, 1 GiB is 3-6% faster. Those runs are kept in old-sampler and are not reported. All 48T rows here were re-measured with a fork-free sampler (pagesampler.py, SCHED_IDLE), and the per-run watcher shell also drops to SCHED_IDLE while the run is going. 1T rows were kept (47 idle cores: the forks rarely landed on the solver); spot check, same cubes, old sampler (repeat 1) vs new (repeat 2): cubeoptrsh8 1G 1T 3 cubes 16.890 -> 15.799 s (-6.5%); h48h7 1G 1T 2 cubes 211.203 -> 217.062 s (+2.8%); nxopt31 THP 1T 25 cubes 13.916 -> 14.087 s (+1.2%); vcube112 THP 1T 25 cubes 9.072 -> 8.961 s (-1.2%).

Remaining asymmetries:

  • cubeopt30 and cube48opt10 are prebuilt binaries (GCC 9.4, "use sse, bmi2"); they cannot be rebuilt.
  • nissy H48 runs through its Python module (as the harness does); the time is taken around each nissy.solve call, so the Python call overhead (microseconds) is included. nissy's C shell (./run) loads the table per invocation, so it is not usable for a batch.
  • Different table families: egg-solver and nissy use H48 tables (egg-solver's hN keep different EO bits than nissy's), cube48opt its own H48 variant, nxopt and vcube their coset tables; same-size groups are approximate (see "size").
  • Thread semantics: nxopt and vcube cannot put several threads on one cube, so they have no latency rows at 48T; their 48T throughput uses the harness formula (sum of per-cube times / 48), which leaves out the idle tail, while egg-solver's batch rows are wall / cube including its tail.
  • nissy's node counts vary run to run (uninitialized task rank, competitor finding #7); its h11 table is slightly inadmissible (#1).
  • cube48opt-rust (github.com/2017YANR02/cuberoot.me solver/experiments/cube48opt-rust at 1effb34, a Rust port of cube48opt1-9 plus its own Opt10): its latency mode is capped at 18 search threads (MAX_SEARCH_THREADS), so its 48T latency rows run on 18 threads (its cap); its throughput rows use 48 (one cube per thread). It allocates its table with malloc (4 KiB pages as shipped): THP = hugeshim thp mode, 1G = hugeshim arena, as nxopt and nissy. Opt7/Opt8 tables were made by its own init (SHA-256 = upstream's published hashes). Opt10 reads cube48opt10's raw file through a loader-only shim: with cube48opt10's unread block minima (15) written as 10 the bytes equal its official Opt10 payload (SHA-256 2ce3d57d..., re-verified on every load); 959 of 962 functions (every search function) are byte-identical to the official build. Builds screened: shipped, native, PGO, and its optional x86 table prefetch (pf / pfnative, off in its official sets).

cube48opt10's table vs egg-solver h10

cube48opt10's h48prun31h1.dat (made by its first run in an empty folder) against egg-solver's h10 table (data part; ours has a 4 KiB trailer after it). A static analysis of the cube48opt10 table found the same size, base (10) and 2-bit code meaning, with one expected benign difference: the unread minimum nibble of groups whose entries are all above the base (15 in cube48opt, 11/12 in ours). gen compare reads both as egg-solver h10 tables; the byte compare counts benign vs real differences and the histograms of both files (equal histograms with many real differences = the same values in a different index order).

Result: different tables. Apart from the benign unread nibbles there are also real differences, so cube48opt10's file is neither our h10 nor a reordering of it.

  • Bytes: 29,791,179,308 of 31,130,910,720 bytes (95.7%) differ for real. 172,108,390 differences (8.8% of the 1,945,681,920 groups) are the benign kind: an unread minimum nibble, 15 in theirs and 11 (157,973,301) or 12 (14,135,089) in ours.
  • First real difference: offset 0, the minimum byte of group 0. Ours is 06; theirs is 00, the solved state at index 0. Group 0 then holds mostly codes 1/2 in ours and codes 0/1 in theirs.
  • Entries (gen compare, both read as h10 base 10): 69,126,743,843 of 120,389,068,800 entry codes differ (57.4%). 913,531,947 group minima ≤ base differ, plus 856,376,982 unread ones.
  • Not a permutation:
    • The code histograms are close but not equal. Ours: 0: 1,133,240,200, 1: 11,196,287,163, 2: 64,164,706,157, 3: 44,138,045,520. Theirs: 1,134,918,810 / 11,222,950,329 / 64,306,616,699 / 43,967,793,202.
    • Ours has 170.3M more entries at code 3 (≥ 13) and 0.15-0.24% fewer at codes 0-2, so ours is slightly higher (stronger) on average. Theirs matches cube48opt10's own generation printout exactly: 11: 11,222,950,329, 12: 64,306,616,699.
    • This fits a different index mapping (coset numbering or which EO bit is dropped from h11), not a different file format: size, base, the 2-bit codes and the group-minimum slot agree, as the static analysis found.
  • What it means for the comparison: node counts and timings are unaffected, since each solver reads its own table. For cube48opt-rust, the file cannot be swapped with ours.
